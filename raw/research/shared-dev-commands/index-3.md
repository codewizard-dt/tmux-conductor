# Research: Re-verify shared-dev-commands gaps + scope Phases 1-4 (ROADMAP-020 Phase 0)

> Builds on [index.md](index.md) (original gap analysis) and [index-2.md](index-2.md) (a concurrent, narrower pass that already turned Phase 1 — the split-brain fix — into a line-cited implementation plan). This pass does two things index-2.md didn't: (1) re-verifies *every* assumption in index.md against the current tree, confirming nothing has drifted since 2026-09-13 beyond cosmetic line-number shifts, and (2) goes deep on the three areas index-2.md left alone — project-scoping (Phase 2), UI/UX parity (Phase 3), and the agent-facing skill/script (Phase 4) — then answers the scoping question: one task for all of Phases 1-4, or one per phase. **Recommendation: one task per phase**, matching what is already happening in practice (index-2.md exists specifically to scope Phase 1 alone).

## Research Questions
- Do index.md's Gap 1 (split-brain), Gap 2 (no `project_id`), and Gap 3 (no agent-side discovery) still hold against the current working tree, unchanged in substance?
- **Project-scoping**: what exact migration shape should `bg_processes.project_id` take, should it be nullable or required, and how should project-filtered listing be exposed to both the UI and the future skill/script?
- **UI/UX**: what does "parity with agents" concretely mean for `BgProcessSection`/`AddBgProcessForm.tsx` — grouping, empty states, project selector — given the `groupByProject` pattern `AgentList.tsx` already uses for agents?
- **Skill/script**: what command surface, `SKILL.md` conventions, and host-server-unreachable fallback should the agent-facing `dev-commands` skill use, given what this user's own `~/.claude/skills/` and this repo's `.claude/skills/` actually look like today (not just Anthropic's documented pattern)?
- Single task vs. multi-task: given the size/risk of each phase and that Phase 1 is already being scoped as its own task elsewhere in this session, what's the correct task-filing structure for Phases 1-4?

## Current State (Codebase) — re-verified live, 2026-09-13

**Gap 1 (split-brain) — confirmed unchanged**, and independently re-confirmed in more depth by [index-2.md](index-2.md) (exact call sites, plus a *wider* split than originally scoped: `AGENT_BG_LINKS` is split too, and the bash side has already fully cut over to reading the link from SQLite via `scripts/lib/db.sh`'s `load_agents()` SQL join, not from `conductor.conf` at all). Not re-litigated here — see index-2.md for the full plan.

**Gap 2 (no `project_id`) — confirmed unchanged.** `bg_processes` schema (`host-server/db.ts:299-305`) still has no `project_id` column, while `agents` (296), `tasks` (322-323), and `schedules` (311-312) all do. `BgProcess`/`BgProcessRow` (`db.ts:37-43`, `139-145`) and the frontend `BgProcess` interface (`frontend/src/components/AgentList.tsx:55-64`) both lack `projectId`/`projectName` fields — neither side has drifted toward adding it independently.

**Gap 3 (no agent-side discovery) — confirmed unchanged.** No `~/.claude/skills/dev-commands` exists; `CONDUCTOR_STATE_DIR`/`CONDUCTOR_LOG_DIR` are still unconditionally exported into every agent's launch env regardless of link status (`scripts/conductor.sh:65`, `:83`; `scripts/spawn.sh` mirrors this) — the env-var precondition for the skill/script is intact and unchanged.

**Precedent for the `project_id` migration** — `db.ts`'s `runMigrations` is at `schema_version` **8** (last bump: `if (version < 8)` block, TASK-125's `tasks_v8` rebuild, `db.ts:410-443`). A new `bg_processes.project_id` migration would be `if (version < 9)`. The closest prior art for "add a nullable `project_id` FK to an existing table with a name-uniqueness index" is the **v2** migration (`db.ts:335-357`), which rebuilds `agents` into `agents_v2` (adding `project_id INTEGER REFERENCES projects(id) ON DELETE SET NULL` and two partial-unique indexes: `idx_agents_project_name` scoped `WHERE project_id IS NOT NULL`, `idx_agents_null_name` scoped `WHERE project_id IS NULL`) rather than a plain `ALTER TABLE ... ADD COLUMN`. `bg_processes.name` already has a *global* `UNIQUE` constraint (`db.ts:301`, `CHECK (name GLOB '[A-Za-z0-9_-]*')` + column-level `UNIQUE`) — unlike `agents`, which is unique only *within* a project. This is a real design fork: does adding `project_id` to `bg_processes` also relax its uniqueness to per-project (mirroring agents), or does it stay globally unique regardless of project? See Constraints below — the answer is forced by an existing constraint the prior research didn't examine (tmux window-name global uniqueness), not a free choice.

**UI precedent for "parity with agents"** — `AgentList.tsx`'s `groupByProject` (`:1595-1604`) is a simple cluster-consecutive-same-project helper: given a *sorted* list, it walks it once and starts a new group whenever the project label changes, producing `{ project: string | null; agents: Agent[] }[]` that the render pass turns into a sub-header per group. `BgProcessSection` (`:1279-1289`) today is a flat, unsorted, ungrouped list — no empty-state message (`if (bgs.length === 0) return null`, i.e. the whole section vanishes rather than showing "no background processes" the way `AgentList`'s own `agents.length === 0` branch shows `"No agents registered."` at `:1630`). `AddBgProcessForm.tsx` has no project selector at all — cross-check against `AddAgentForm.tsx`'s pattern (`:192-215`): a controlled `<select>` bound to `selectedProjectId`, defaulting to a "no project" empty-string option, that also cross-populates a dependent field (there, `launchCmd` from the project's `defaultLaunchCmd`; for bg processes there is no equivalent side effect, so this is simpler — just the `<select>` itself, required per the roadmap's own wording).

**Skill/script precedent — this repo/user has *zero* prior art for a bundled `scripts/` skill.** Checked both scopes:
- User-global `~/.claude/skills/*` (66 entries, e.g. `research`, `power-mode`, `demo`) — every one inspected is a single `SKILL.md` file (or `SKILL.md` + a couple of loose reference `.md` files, e.g. `demo`'s 4-file dir), never a `scripts/` subdirectory with an executable wrapper.
- Project-scoped `.claude/skills/typecheck/SKILL.md` — same: single file, no bundled script.

This directly contradicts index.md's citation of "the System Skill Pattern" (`SKILL.md` + `scripts/`) as something "appropriate for a thin CLI over the existing log/state-file conventions" [S6 in index.md] — that pattern is Anthropic's documented convention, not this user's established local convention. The repo *does* have a strong, working precedent for **installing** something into `~/.claude/` from a repo-tracked source: `install-hooks.sh` (repo root, 173 lines) copies JS hook files plus a shared lib into `~/.claude/hooks/tmux-conductor/` and merge-registers them into `~/.claude/settings.json` with dedup-by-command, explicitly preserving foreign entries. If Phase 4 does ship a bundled script (not just a `SKILL.md` with inline Bash), this installer is the pattern to mirror — not a fresh design.

## Key Findings

- Every claim in index.md still holds verbatim against the current tree; only line numbers drifted by single digits (e.g. `CONDUCTOR_STATE_DIR` export moved from `scripts/conductor.sh:61-66,84` to `:65,83` — a one-line net shift, not a behavior change) [S1][S2].
- index-2.md, written concurrently in this same session by a separate research pass scoping Phase 1 alone, independently reaches the same split-brain conclusion and *extends* it (the `AGENT_BG_LINKS` half is also split, and worse: the host-server's conf-write side is producing data the bash scripts no longer read at all, since they migrated the link lookup to a SQL join in `scripts/lib/db.sh`'s `load_agents()`) [S3].
- `bg_processes.name` is a *global* `UNIQUE` column-level constraint today (not project-scoped like `agents.name`), and `POST /bg-processes` additionally checks name collisions against **agent window names too** (`conf.bgProcesses.some(...)` alongside a `isTmuxWindowPresent` check, both cited in index.md's Constraints) — because tmux window names are session-global. Adding `project_id` must NOT relax this to a per-project unique index (the way `agents_v2`'s migration did for agents), because two bg processes in different projects could then collide on a tmux window name with no uniqueness check catching it. `project_id` here is classificatory metadata for filtering/display, not a uniqueness scope [S4].
- `AddBgProcessForm.tsx` fetches only `{name: string}[]` from `/status` for its agent-link picker (frontend/src/components/AddBgProcessForm.tsx:11-13, 26-32) — it does not currently know about projects at all, so wiring in a project `<select>` needs a **new** fetch (`GET /projects`, already exists and is used by `AddAgentForm.tsx`) rather than reusing existing local state [S5].
- `BgProcessSection` currently has no empty-state message and no sorting — unlike `AgentList`'s main render path, which explicitly branches on `agents.length === 0` to show "No agents registered." Achieving stated "parity with agents" requires adding both, not just grouping [S5].
- No skill in this user's `~/.claude/skills/` (66 skills surveyed) or this repo's `.claude/skills/` bundles a `scripts/` directory — the "SKILL.md + scripts/" shape recommended by the prior research has no local precedent to follow, only Anthropic's own documentation. `install-hooks.sh` is the closest local precedent for *installing* repo-tracked material into `~/.claude/`, but it installs hooks, not skills [S6][S7].
- A second live agent process in this same session is already treating Phase 1 as a standalone, independently-scoped task (index-2.md's own "Next Steps": "`/task-add` this exact scope as the ROADMAP-020 Phase 1 task (already in progress in this session)") — i.e., the per-phase task split is already the de facto execution pattern, not just a recommendation [S3].

## Constraints

- tmux window-name global uniqueness (documented in CLAUDE.md, enforced today via `conf.bgProcesses.some(...)` + `isTmuxWindowPresent`) forces `bg_processes.project_id` to be **classificatory only** — the `name` column's existing global `UNIQUE` constraint must NOT be relaxed to a per-project partial unique index when the migration lands, unlike the `agents_v2` precedent it otherwise resembles.
- `project_id` must be **nullable** (`INTEGER REFERENCES projects(id) ON DELETE SET NULL`, mirroring `agents`) — not required at the DB level — because (a) `seedFromLegacy()`'s one-time import of pre-existing `conductor.conf`-defined bg processes has no project context to assign, and (b) the roadmap's own Phase 3 wording ("required project selector") is a **UI-level** requirement for new bg processes created through the dashboard going forward, not a backfill guarantee for existing rows or for the DB schema itself. Conflating the two would make the migration a breaking change instead of additive.
- `db.migration.test.ts` has `CREATE TABLE bg_processes` fixtures at two schema-version snapshots (lines ~129 and ~812, confirmed present) that assert column sets at those historical versions — a new `project_id` migration must add a **new** post-migration fixture/assertion pair there, not edit the existing historical ones (they intentionally freeze what a *pre-migration* DB looked like).
- Any project-filtered listing endpoint should follow the existing `listTasksByProject`/project-scoped query pattern already in `db.ts` (e.g. `listTasksByProject(db, projectId)`) rather than inventing a new filtering idiom.
- Per CLAUDE.md: `.env` files stay off-limits (not relevant — no secrets in this feature); all host-side scratch work goes in `./tmp/`, never `/tmp`.
- Phase 1 (split-brain) must land before Phase 2 (`project_id`) — index-2.md makes this explicit ("Phase 2 becomes unblocked" once Phase 1 is done) — there is no point adding a scoping column to a table two different write paths disagree about.

## Solution Comparison — task-filing structure for Phases 1-4

| Criteria | A. One task per phase (4 tasks, sequenced by `depends_on`) | B. One mega-task covering all of Phases 1-4 | C. Two tasks (backend: split-brain+scoping combined; frontend+skill: UI+script combined) |
|---|---|---|---|
| **Approach** | Separate `TASK-NNN` per roadmap phase, `depends_on` chaining (2→1, 3→2, 4→1) | Single task with four step-groups | Split along the backend/frontend seam instead of the phase seam |
| **Pros** | Matches existing granular task-sizing convention in this repo (TASK-150/152/153 etc. average ~1 file-area each); matches what's *already happening* — Phase 1 is being scoped standalone right now (index-2.md); each phase gets its own focused UAT; a stalled/blocked phase doesn't hold up the others | Single UAT pass covers the whole feature end-to-end in one go; no cross-task `depends_on` bookkeeping | Fewer files to juggle than A; backend and frontend can proceed somewhat in parallel |
| **Cons** | More task files to create and track; requires `depends_on` discipline to enforce Phase 1 → 2 → 3, and 4 can run parallel to 2/3 | Violates the split-brain-fix-must-land-first ordering constraint within a single task's step list (risk of the "fix the split-brain" step getting rushed alongside three other concerns); a single huge diff is harder to review/UAT incrementally; contradicts the concurrent Phase-1-only task-add already in flight | Phase 2 (project_id) has both a DB half and a UI half that would need to straddle both of the two tasks anyway, so the seam doesn't actually reduce cross-task coordination — it just moves it |
| **Complexity** | Medium (4 small, well-bounded units) | High (one large unit spanning migration + routes + UI + a wholly new user-global artifact) | Medium-High (the straddling problem above) |
| **Dependencies** | None new | None new | None new |
| **Codebase fit** | High — matches this repo's demonstrated task-granularity norm and the split-brain-first ordering already established by index-2.md | Poor — no other active task in `wiki/work/tasks/` spans this many unrelated subsystems (migration + 2 route families + 2 components + a new `~/.claude/` artifact) in one file | Medium — no clean precedent for a backend/frontend task split in this repo either |
| **Maintenance** | Low — each task closes independently, each with its own UAT | Medium — one giant UAT walkthrough covering unrelated failure surfaces | Medium |

## Recommendation

**Recommended: Option A — one task per roadmap phase**, `depends_on`-chained. This is not just the better-fitting option in the abstract; it's already the pattern in motion (index-2.md exists specifically because another process in this session is scoping Phase 1 as its own task right now). Concretely:

- **Phase 1 task** (split-brain fix): scope is already fully specified in [index-2.md](index-2.md) — do not duplicate that work here; whoever files it should cite index-2.md directly.
- **Phase 2 task** (`project_id` on `bg_processes`): `depends_on` the Phase 1 task. Migration = `if (version < 9)` rebuild-or-add-column (decide `ALTER TABLE ADD COLUMN` vs. full rebuild during implementation — unlike `agents`, no uniqueness-index change is needed here, so a plain `ALTER TABLE bg_processes ADD COLUMN project_id INTEGER REFERENCES projects(id) ON DELETE SET NULL` likely suffices and is simpler than the `agents_v2`-style rebuild); extend `BgProcess`/`BgProcessRow`/`mapBgProcess`; add a project-filtered listing path following `listTasksByProject`'s pattern; new `db.migration.test.ts` fixture pair for the post-migration schema.
- **Phase 3 task** (UI/UX): `depends_on` the Phase 2 task (needs `projectId`/`projectName` on the wire first). Add a required `<select>` to `AddBgProcessForm.tsx` (new `GET /projects` fetch, mirroring `AddAgentForm.tsx`'s pattern, not reusing the existing `/status`-derived agent list); extend the frontend `BgProcess` interface with `projectId`/`projectName`; group `BgProcessSection` using a `groupByProject`-style cluster (reuse or extract `AgentList.tsx`'s existing helper rather than reimplementing it) with a project sub-header per group and an "unscoped" group for `projectId: null`; add the missing empty-state message (`bgs.length === 0` today just hides the section — should instead read like `agents.length === 0`'s "No agents registered." treatment) to reach genuine parity.
- **Phase 4 task** (agent-side skill): can run in parallel with Phases 2/3 (`depends_on: [Phase 1]` only, `parallel_safe_with: [Phase 2, Phase 3]`) — it only needs the *existing* `bg-<name>.log`/`.state` conventions and `CONDUCTOR_STATE_DIR`/`CONDUCTOR_LOG_DIR`, none of which change in Phases 2/3. Given the **zero local precedent for a bundled-`scripts/` skill** found in this pass, the implementing task should explicitly decide between (a) a `SKILL.md`-only skill with the `list`/`status`/`tail` logic written as inline Bash the agent runs directly via the Bash tool (zero new install machinery, matches 100% of this user's 66 existing skills), or (b) a `SKILL.md` + `scripts/dev-commands.sh` pair requiring a new `install-dev-commands-skill.sh`-style installer mirroring `install-hooks.sh`'s copy-and-merge idempotency — recommend **(a)** unless the script grows enough internal logic (e.g. JSON parsing, retry logic against the host-server API) that inlining it in `SKILL.md` becomes unwieldy, since (a) has a real local convention behind it and (b) doesn't.

**Risks and mitigations:**
- **Phase-ordering drift** (someone starts Phase 3 before Phase 2 lands) — mitigated by explicit `depends_on` in each task's frontmatter; `/task-audit`'s dependency graph will surface a violation.
- **Duplicate Phase 1 task-add** — a second agent in this same session already has Phase 1 fully scoped (index-2.md); this Phase 0 task must not re-scope or re-file Phase 1, only reference index-2.md and hand the phase 2-4 breakdown to whoever runs `/roadmap-next` next.
- **`bg_processes.name` uniqueness scope decision reversing silently** — flag explicitly in the Phase 2 task's Approach section (global uniqueness stays; `project_id` is classificatory only) so a future implementer doesn't default to copying the `agents_v2` per-project-unique-index pattern by habit.
