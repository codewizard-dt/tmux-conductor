# Research: How to Evaluate Agent State Transitions

> tmux-conductor already runs a three-tier evaluation strategy for its from/to status-transition heuristics (unit-level branch tests, a golden pane-snapshot fixture corpus shared across its two independent detectors, and a production transitions.jsonl log with an offline false-positive-rate reporter) — this is a mature, working implementation of exactly the pattern external testing literature recommends for heuristic state detectors (table-driven transition tests, golden/characterization fixtures, production replay). The main gap against that literature: coverage stops at "0-switch" (every individual transition exercised once) with no "1-switch" coverage (consecutive transition *pairs*, e.g. does a busy→awaiting→busy flap get handled correctly across two ticks), and the production false-positive measurement self-labels using a second heuristic (dialog-marker regex) rather than a human-audited ground-truth sample, which academic work on label-free FPR estimation flags as a real source of underestimation.

## Research Questions
- What does tmux-conductor currently do to evaluate whether its agent status-transition detection (`to`/`from` state, with reason/snapshot) is correct?
- Is this architecture (unit tests + golden fixtures + production log) a recognized testing pattern, and what do external sources say about doing it well?
- Where does the current implementation's coverage stop, and what would extending it look like?
- How should correctness be measured in production when there is no ground-truth label for "was this transition real"?

## Current State (Codebase)

tmux-conductor detects agent status via two independent, parallel-maintained implementations — `host-server/state.ts`'s `detectAgentStatus()` (TypeScript, 18 distinct `return` sites across 4 precedence branches: no-window → exited/pane-dead → hook state-file → regex fallback) and `scripts/monitor.sh`'s `is_idle()` (bash, same precedence order) — and every transition either one detects is written to a project-wide `DetectionReason` union (`host-server/state.ts:9-12`: `no-window | exited | starting | state-file | busy-recovered | awaiting-pattern | regex-fallback | inventory-timeout | background-job`). The evaluation strategy that has grown up around this split cleanly into three tiers:

**Tier 1 — unit/branch tests (white-box, synthetic).** `host-server/state.test.ts` has one `test(...)` per numbered return site of `detectAgentStatus` ("site 1" through "site 18"), each constructing a minimal state-file + pane-tail fixture by hand and asserting the exact `{state, reason, matchedPattern}` triple. This is "0-switch coverage" in state-transition-testing terms [S4]: every individual transition/branch is exercised at least once, with no attention to transition *sequences*.

**Tier 2 — golden fixture corpus (black-box, shared across both detectors).** `host-server/fixtures/awaiting-panes/manifest.json` holds real captured pane text (one `.txt` per case) plus `{launch, stateFile, ageS, expected: {state, reason}}` metadata, covering the hardest cases for the `awaiting` classification specifically (AskUserQuestion dialogs, Y/n confirms, plan-approval screens, UAT verdict idle-files, bare `>` prompts, busy-footer-with-a-literal-"?"-in-the-text false positives, Codex "Running" scrollback, etc.). This single manifest is consumed by **both** `state.test.ts` (TS side) and `scripts/verify-awaiting-detection.sh` (bash side, which structurally extracts `is_idle`/`awaiting_window`/`busy_visible` etc. out of the live `monitor.sh` text with a stubbed `tmux` on `PATH`, rather than re-implementing the logic in the test) — a textbook golden-master / characterization-test setup [S5] applied twice to keep two independently-maintained implementations from silently drifting apart (`wiki/knowledge/concepts/dispatch-path-parity.md`, `wiki/knowledge/concepts/agent-state-determination.md`).

**Tier 3 — production log + offline analysis (field evaluation).** Every observed transition, from either detector, lands in `logs/transitions.jsonl` as one record: `ts, agentId, agent, from, to, reason, matchedPattern, stateFileAgeS, windowPresent, queuedTasks, paneTail` (host-server's `appendTransitionLog`, `host-server/index.ts:503-514`, called from `pollAndDiff`, `host-server/index.ts:2836-2965`) or the bash-equivalent subset (`emit_transition_jsonl`, `scripts/monitor.sh:512-543`). `scripts/report-false-awaiting.mjs` reads this log read-only and, for every `to: "awaiting"` record, flags it as a likely false positive if the last 8 non-blank `paneTail` lines contain neither a dialog marker (`Enter to select`, `[Y/n]`, etc.) nor — inversely — flags it if `esc to interrupt` (the busy spinner) is visible, which would mean the agent was never actually waiting. This script, not a human-labeled ground truth, is the project's current precision/recall proxy; its last recorded baseline run (TASK-0231, 2026-09-20) found 329 `awaiting` transitions with 178 (54%) lacking a dialog marker and 21 (6%) with the busy spinner visible — numbers that drove the BUG-0013 fix and are logged verbatim in `wiki/log.md`.

The pattern recurs project-wide as "two implementations, one fixture set": `wiki/knowledge/concepts/dispatch-path-parity.md` documents the same discipline applied to the dispatch path, not just status detection — this is a named, cross-referenced architectural convention in this codebase, not a one-off.

A related, narrower prior research pass (`raw/research/monitor-sh-transition-emit-testability/index.md`, 2026-09-13) specifically worked out how to unit-test `monitor.sh`'s JSONL-emission function in isolation (structural function-boundary extraction + stubbed `tmux`, never sourcing the whole file, since `monitor.sh` has an unconditional infinite poll loop and hardcoded real log paths) — that is the technique `verify-awaiting-detection.sh` and `verify-transitions-jsonl-emit.sh` both now use. Another prior pass (`raw/research/transition-observability/index.md`, 2026-09-13) is the research that originally proposed `transitions.jsonl` itself, citing an agent-observability tracing framework ("AgentTrace") and general audit-log guidance as its external grounding — both already implemented, so this report does not re-derive that design.

## Key Findings

- **F-1**: The current architecture already matches the three canonical techniques external testing literature recommends for a heuristic/rule-based state detector: table-driven transition tests at the unit level [S4], golden/characterization fixtures for the hard cases [S5], and production-traffic-derived regression data at the field level [S6]. This is not a gap to fill so much as a pattern to recognize and extend deliberately. *(codebase, cross-referenced with web)*
- **F-2**: Formal state-transition-testing terminology calls exercising every individual transition once **"0-switch coverage"** and exercising every consecutive *pair* of transitions **"1-switch coverage"** (catches defects "where the system's history matters") [S4]. tmux-conductor's Tier 1 and Tier 2 tests are both 0-switch: every fixture is evaluated by calling `detectAgentStatus`/`is_idle` exactly once against a single snapshot. There is no test anywhere in the suite that constructs a *sequence* of two or more polls and asserts on the resulting from→to pair — e.g., nothing verifies that a `busy→awaiting→busy` flap within one `2×POLL_INTERVAL` window is handled the way the code's own stall/recovery logic intends, or that an `idle→busy→idle` sequence correctly avoids a spurious double-dispatch. The `stateFileAgeS`-driven recovery branches (`busy-recovered`, `inventory-timeout`) are exactly the kind of "history matters" logic 1-switch coverage targets, and they are currently tested only with a single synthetic snapshot carrying a pre-set fake age, not a simulated sequence of real polls. *(codebase, inference against S4)*
- **F-3**: Michael Feathers' "characterization test" / "golden master" pattern [S5] is explicitly meant for capturing *existing* behavior over hard-to-specify legacy logic, with the caveat that golden fixtures only catch a regression if the fixture set already contains an input that exercises it [S5 differential-audit note]. `host-server/fixtures/awaiting-panes/manifest.json` currently has 14 cases, all hand-picked for the `awaiting` classification specifically — there is no equivalent golden corpus for the `busy`/`idle`/`stalled`/`exited` classifications, even though those are equally heuristic (regex-fallback, state-file age thresholds). A newly-introduced bug in, say, the `stalled`-timeout branch would have no fixture-level safety net analogous to what `awaiting` now has. *(codebase, inference against S5)*
- **F-4**: `scripts/report-false-awaiting.mjs`'s false-positive proxy (dialog-marker regex absent ⇒ likely false positive) is itself a second heuristic layered on the first, not a ground-truth label. Academic work on estimating false-positive rate from unlabeled production data [S1][S2][S3] converges on two points directly relevant here: (a) a classifier's own correlate cannot safely validate itself — one source warns explicitly that "using the model to directly clean its own validation data leads to underestimates even if total error is low" [S3] — and (b) the more defensible alternatives are either a small human-audited sample of flagged records (to estimate precision and extrapolate) or comparing against an independent second method (the Hui-Walter paradigm) [S1]. tmux-conductor's existing dual-detector setup (TS vs. bash) is structurally close to a Hui-Walter-style second method, but `report-false-awaiting.mjs` does not currently cross-check *which* detector produced each `awaiting` record or compare the two detectors' verdicts against each other in production — it only inspects the `paneTail` text with its own separate heuristic. *(codebase + web)*
- **F-5**: The project's own prior research (`transition-observability`) already identified and closed the biggest historical gap — going from "no snapshot captured at transition time" to "every transition carries its own pane-text snapshot plus detection reason" — which is the precondition for everything above. Without `paneTail` in `transitions.jsonl`, none of Tier 3's false-awaiting analysis, nor any future human-audit sampling, would be possible at all. *(codebase)*
- **F-6**: This codebase has an established, working convention for turning a *found* production bug into a *permanent* regression fixture: BUG-0013 → TASK-0231 added 14 new cases to `host-server/fixtures/awaiting-panes/manifest.json`, each one a real captured pane snapshot from (or modeled on) an observed false transition, consumed by both detectors' test suites going forward. This loop (production anomaly → golden fixture) already exists for `awaiting`; it has not yet been generalized into a standing procedure that runs after *every* `report-false-awaiting.mjs`-flagged batch, or extended to the other state pairs noted in F-3. *(codebase)*

## Constraints

- **Two independent detectors, two languages, must not drift** — any extension to coverage (more fixtures, sequence tests, cross-detector checks) needs to either run against both `state.ts` and `monitor.sh`, or explicitly document why one side is exempt (the codebase already notes one known, accepted gap this way: `EDGE-007` in `UAT-0231`, a Codex-with-busy-state-file divergence between `state.ts` and `monitor.sh` left unresolved as an acknowledged, out-of-scope difference rather than silently ignored).
- **No live tmux/DB/wall-clock sleeps in unit tests** — `monitor-sh-transition-emit-testability`'s established constraint (the project's own UAT-generation promotability bar excludes tests needing a live server, live tmux session, or `POLL_INTERVAL`-scale sleeps) still applies to any new sequence-based (1-switch-style) test; such a test would need synthetic, directly-called invocations of the detection functions with manually-advanced fake ages/state-file contents across two or more calls, not a real poll loop.
- **No log rotation, unbounded growth already accepted** — `transitions.jsonl` has no rotation by explicit prior decision; any new analysis tooling (e.g. a human-audit sampler) must stay read-only against this file, matching `report-false-awaiting.mjs`'s own convention, and should not assume the file is small.
- **Sensitive pane content** — `paneTail` can carry prompts, file paths, and task text; any tooling that surfaces sampled transitions to a human for audit-labeling should reuse the existing acceptance-of-risk precedent (dispatch.jsonl/transitions.jsonl already accept this) rather than introduce new redaction machinery out of scope.
- **No new test framework** — the project's bash-side testing convention is plain `scripts/verify-*.sh` files with structural extraction, not bats/shunit2; any new bash-side coverage should follow that precedent, matching `verify-awaiting-detection.sh`'s established shape.

## Recommendation

**Recommended approach: B + D as the next concrete steps, with C as an ongoing practice rather than a one-time task.**

- **B (1-switch sequence tests)** is the most leveraged next step because it targets a *named, already-tested-for-the-single-call-case* class of logic (`busy-recovered`, `inventory-timeout`, the awaiting↔busy revert branches) where the existing 18-site tests only ever call the detector once per test. Add a small number of new `state.test.ts` cases that call `detectAgentStatus` twice in sequence with a manually-advanced fake state-file mtime/content between calls (no real sleep, no live tmux — matches `monitor-sh-transition-emit-testability`'s established constraint) and assert on the from→to pair the second call produces, not just its standalone state. Mirror on the bash side only if `verify-awaiting-detection.sh`'s extraction harness can be reused without a live poll loop; otherwise document the bash-side gap the same way `EDGE-007` is already documented.
- **D (human-audit calibration)** is cheap and directly answers the one finding ([F-4]) grounded in external literature that the project hasn't addressed: build a small, read-only companion to `report-false-awaiting.mjs` that samples a handful of recent `awaiting` (and, once C exists, other-state) transitions, shows the snapshot, and records a human verdict into a local file — then report how often the existing dialog-marker heuristic agrees with that human verdict. This gives an actual precision estimate for the existing proxy instead of trusting it by construction.
- **C (extend golden fixtures beyond `awaiting`)** should be treated as the standing procedure the project already half-follows (BUG-0013 → TASK-0231's fixture additions) rather than a single task: whenever `report-false-awaiting.mjs` (or its generalized D-successor) surfaces a genuinely misclassified transition for *any* state pair, its snapshot becomes a new fixture in `host-server/fixtures/awaiting-panes/manifest.json` or a sibling `*-panes` directory, closing the loop the way the project's own log entries already describe doing for `awaiting`.

### Implementation outline
1. Add 2-3 sequence-based tests to `host-server/state.test.ts` for the `busy-recovered` and `inventory-timeout` branches, calling `detectAgentStatus` twice with a controlled fake age between calls.
2. Write a small read-only `scripts/audit-sample-transitions.mjs` (or extend `report-false-awaiting.mjs`) that samples N records from `logs/transitions.jsonl`, prints each with its snapshot for a human verdict, and compares the result against the existing dialog-marker heuristic.
3. Treat any future `report-false-awaiting.mjs`-flagged (or human-audit-flagged) misclassification as fixture material: capture its `paneTail` into a new `.txt` fixture and add a manifest entry with the corrected `expected` value, following the exact BUG-0013/TASK-0231 precedent.

### Risks and mitigations
- **Risk**: sequence tests (B) could overfit to today's exact recovery-threshold numbers (`pollInterval * 2`, `stallTimeout`) and become brittle if those tunables change. **Mitigation**: parameterize the test's fake ages off the same `conductor.conf` tunables the production code reads, not hardcoded seconds.
- **Risk**: a human-audit sampler (D) run too infrequently or on too small a sample gives a false sense of calibration. **Mitigation**: treat its output as a periodic spot-check (e.g. re-run after any detection-logic change, not a one-time report), consistent with how `report-false-awaiting.mjs` is already re-run after fixes (its own doc comment records a "pre-fix baseline").
- **Risk**: extending golden fixtures (C) to every state pair could grow the manifest unmanageably. **Mitigation**: keep the existing one-manifest-per-hard-classification structure (a sibling manifest per state pair, not one giant file) and only add a fixture when a real misclassification was observed — mirroring the "golden fixtures from legacy/observed behavior, not speculative cases" framing in characterization-testing literature [S5].

### Alternative if constraints change
If the project ever adopts a bash test framework (bats-core or similar) — currently explicitly out of scope per prior research — the structural-extraction harnesses (`verify-awaiting-detection.sh`, `verify-transitions-jsonl-emit.sh`) should migrate into it rather than staying ad hoc, which would also make 1-switch-style sequence tests easier to express on the bash side.
