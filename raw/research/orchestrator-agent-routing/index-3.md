# Research Round 3: Assumption Audit + the Missing "Specialized Agent Catalog" Layer

> Builds on [index.md](index.md) and [index-2.md](index-2.md); this round does not repeat their findings on tmux-conductor's current mechanical dispatch, the orchestrator-worker/supervisor literature, or the ephemeral-worker-per-task ecosystem survey — those still stand. This round was prompted to (a) explicitly audit the assumptions embedded in rounds 1 and 2, and (b) push further into "specialized agents" and "Orchestrator Agent" specifically, including a "curated list of tools for specialized sub-agents" the earlier rounds treated only in passing. The headline finding: rounds 1–2 quietly collapsed two independent design axes — *who decides which agent gets a task* (orchestrator/router) and *what agents exist to be decided among* (a specialized-agent catalog) — into one question. The catalog axis is buildable today, is lower-risk than anything in round 1's A/B/C or round 2's D/E/F, and neither prior round scoped it as its own deliverable.

## Assumptions Identified From Rounds 1–2 (Audited)

1. **Round 2's "ephemeral worker-per-task" tools (dmux, Claude Squad, Vibe Kanban, Crystal) were treated as prior art for "an orchestrator agent," but most of them aren't agents at all — they're deterministic CLI/UI tooling where a human remains the router.** Round 2's own excerpts show this (dmux: "press `m` to merge"; Upsun's "central orchestrator" is a *described role*, not a shipped LLM). Only `claude-vibe-squad`'s Chrono coordinator and `corellis` are actually LLM-driven decision-makers among the 9+ tools surveyed. Round 2's Shape D recommendation is sound as a *provisioning* pattern, but citing it as evidence for "how an orchestrator agent should route" overstates what most of that ecosystem actually does. **Assessment: partially unsound as orchestrator-agent evidence; sound as ephemeral-worker-lifecycle evidence (which is what round 2's actual recommendation used it for — the mislabeling is in how the finding could be read, not in the recommendation itself).**

2. **Neither round examined the one piece of directly-relevant, zero-new-infrastructure prior art already present in this exact working environment: Claude Code's own `.claude/agents/*.md` subagent format and the "Agent Registry" it populates at startup** (name + description + tool allowlist, consulted by a main/orchestrator agent purely via free-text `description` matching — see Key Finding 2). Round 1's S7 cited the Claude Agent SDK's subagent *shape* abstractly but never connected it to the fact that this session's own tool list (`claude-code-guide`, `codebase-inquiry-architect`, `compose-stack-doctor`, `Explore`, `Plan`, `statusline-setup`, `general-purpose`) **is a live, working instance of exactly the "curated list of tools for specialized sub-agents" the user asked about** — one layer up from tmux-conductor, but the closest possible reference implementation, and free to inspect. **Assessment: a genuine gap — the most relevant prior art was sitting in the session's own context and was never cited.**

3. **Round 1's constraint that tmux-conductor's agents are "separate OS processes, not in-process tool-callable subagents" was correctly identified but not connected to a specific, named orchestration-failure axis: "Subagent" vs. "Agent-as-Tool."** Production experience (S38) shows that when a delegate can take conversational control instead of strictly returning a result to the caller, orchestration reliability collapses — "not a prompt problem... an architectural one." tmux-conductor's coding agents, with a live interactive tmux pane as their only interface, are the maximal case of "conversational authority" this literature warns about. **Assessment: round 1's existing recommendation (route only via `POST /queue/:agent`, never `/agents/:agent/keys`) already avoids this failure mode — this round supplies the missing *name* and *evidence* for why that constraint matters, sharpening rather than reversing it.**

4. **Round 2's fleet-churn evidence (S18, a `dispatch.jsonl` tail) was re-checked this round on a fresh tail and still holds** (15 distinct agent names across the last 30 dispatch records) — but a detail neither round noticed: **the names themselves already carry informal specialization** (`tmux-conductor-fe-research`, `tmux-conductor-architect-2`, `tmux-conductor-frontend-2`, `bootstrap-bootstrap-1-copy-2`) via a human-chosen `<project>-<role>-<n>` convention at spawn time. Rounds 1–2 treated the `agents` table as having no specialization signal at all ("no capability/skill metadata exists on the `agents` or `tasks` tables today"); that's true of *structured* metadata, but false of the *informal* signal already present in every agent's own name. **Assessment: a genuine gap — the cheapest on-ramp to a specialized-agent catalog was already visible in existing data and wasn't checked.**

5. **Round 1 dismissed a dedicated orchestrator pane (Option C) partly on cost figures drawn from chat/research-agent benchmarks (~4-15x); round 2 flagged this as an open gap (gap 7) but did not resolve it with coding-specific figures, and this round did not find any either.** No 2026 source found gives a coding-task-specific token-multiplier for orchestrator-worker vs. single-agent dispatch. **Assessment: still an open gap — carry forward unresolved rather than imply confidence that doesn't exist.**

This round directly closes gaps 2 and 4 above with new findings below; closes gap 1 by re-scoping (not discarding) round 2's Shape D; leaves gap 5 explicitly open; gap 3 is closed by naming the failure mode round 1 was already implicitly guarding against.

## Research Questions
- Does the literature support treating "an orchestrator agent" and "a catalog of specialized agents" as the same design decision, or are they separable?
- What does mature, current (2026) prior art say about how a specialized-agent catalog/registry should be shaped, independent of whether an LLM router sits on top of it?
- Is there already-existing prior art for this pattern inside the user's own working environment that rounds 1–2 missed?
- Does live fleet data support formalizing agent specialization as structured metadata, and how cheaply?

## Key Findings

1. **"Orchestrator" and "specialized-agent catalog" are two independent axes, not three alternatives to choose between (as the framing "orchestrator, sub-agents, or a curated list of tools for specialized sub-agents" might suggest).** You can have a catalog with no orchestrator (a human or a fixed rule picks from it — this is round 1's Option A, once agents carry declared roles); an orchestrator with no catalog (ad hoc, per-call reasoning about which agent fits — closer to round 1's Option B before any registry exists); or both together, which every mature 2026 source treats as the production-grade default: TrueFoundry names "a central agent and tool registry: a discoverable catalog with schema validation so different agents find approved available tools dynamically" as the load-bearing layer *beneath* any multi-agent orchestration, not a byproduct of building an orchestrator. [S31] digitalapplied.com's 2026 taxonomy is explicit about sequencing: "Step 5: Move to multi-agent only when single-agent caps out... Justify with measured gain on a specific failure mode." [S32] The registry is buildable and useful *before* that justification exists; the orchestrator is not.

2. **The concrete, minimal-lift reference shape for "a curated list of tools for specialized sub-agents" already exists one layer above tmux-conductor, inside Claude Code itself, and this session is a live instance of it.** Claude Code subagents are markdown files in `.claude/agents/<name>.md` — `name`, `description`, a `tools` allowlist, optional `model` — loaded at startup into what Spring AI's own parallel implementation calls explicitly an **"Agent Registry — a catalog of subagent names and descriptions populated at startup"** that the orchestrating LLM consults purely by reading `description` text to decide when to delegate. [S29, S37] This session's own available-agent list (`claude-code-guide`, `codebase-inquiry-architect`, `compose-stack-doctor`, `Explore`, `Plan`, `statusline-setup`, `general-purpose`, each with a one-paragraph description and a scoped tool list) is exactly this pattern, working, in front of the researcher the whole time. **tmux-conductor's own repository has zero files under `.claude/agents/`** — confirmed this round (`ls .claude/agents/` — directory does not exist) — so this pattern has never been applied even at the one layer where it would require no new tmux-conductor infrastructure at all (though note: that layer governs *this Claude Code session's own* in-process subagents, not tmux-conductor's cross-process fleet — see Constraints).

3. **"Agent-as-Tool" vs. "Subagent" is a named, evidence-backed failure axis directly relevant to tmux-conductor's architecture.** A practitioner building an orchestrator-based system found that giving delegates conversational authority (the ability to talk back to the user / take over the interaction) caused persistent, unfixable-by-prompting failures — "subagents began taking over the conversation in ways that were impossible to reliably prevent using prompts alone... not a prompt problem. It was an architectural one." The fix was to constrain every delegate to the "Agent as Tool" shape: invoked as a function, returns structured output, always hands control back — "tools cannot take over the conversation." [S38] tmux-conductor's coding agents are live, unconstrained terminal sessions — categorically closer to "subagent with full conversational authority" than to "agent as tool" — which is exactly why round 1's constraint (any router may only call `POST /queue/:agent`, never `/agents/:agent/keys`) is not a minor security nicety but the specific architectural guard this literature says is load-bearing.

4. **Live fleet data shows informal specialization-by-naming-convention already happening, which is the cheapest possible on-ramp to a formal catalog.** A fresh check of `logs/dispatch.jsonl`'s last 30 records (re-verifying round 2's S18 finding still holds) shows 15 distinct agent names, several following a legible `<project>-<role>-<n>` pattern already in human use: `tmux-conductor-fe-research`, `tmux-conductor-architect-2`, `tmux-conductor-frontend-2`, alongside pure clone-copy churn (`bootstrap-bootstrap-1-copy-2-copy`, `davill-davill-architect-1-copy`). This means the "no capability/skill metadata exists" constraint from round 1 is true only of *structured* fields — a usable specialization signal already exists as an unstructured naming habit, and formalizing it (splitting a `role` out of the existing name, or adding an explicit `role`/`description` column populated from what the human already types at spawn time) costs far less than inventing a taxonomy from nothing.

5. **Registry-first sequencing has independent 2026 support beyond Azure/AWS (round 1's S15/S16).** The Microsoft Learn orchestrator/subagent architecture guide frames the decision as reuse-driven, not routing-driven: build or adopt a specialist "when specialist agents are already available and optimized for reuse, or explicitly needed to provide tuned or specialized quality for the use case" [S35] — i.e., the catalog is justified by whether specialists are worth having at all, before any question of who routes to them. Levelop's 2026 guide defines the orchestrator role narrowly and downstream of that: "The control layer that turns a collection of specialized agents into a coordinated workflow. It does not usually do the domain work itself." [S36] Both sources treat "do specialized agents exist and are they described well enough to select among" as the prior question to "how does routing work."

6. **Frontier-scale agent swarms (Kimi K2.5/K2.6, 100–300 coordinated specialized sub-agents via Parallel-Agent Reinforcement Learning) are real, current (April 2026) prior art for "specialized agents at scale," but are not actionable here.** [S34] That coordination is trained into the model itself, not built as external orchestration logic — a categorically different lift than anything tmux-conductor could adopt by routing between off-the-shelf Claude Code/Codex/Aider CLI processes. Noted for completeness; explicitly out of scope, not a candidate to compare against A–F.

## Constraints — Update

- **The Claude Code `.claude/agents/*.md` registry pattern (Finding 2) governs *this Claude Code session's own* in-process subagents — it is not a mechanism tmux-conductor's host-server can read or drive.** It is the right conceptual template (name + description + scoped capabilities, consulted by whoever routes), not a literal integration point. tmux-conductor's own specialized-agent catalog would need its own small store (e.g., new `role`/`description` columns on the existing `agents` table, per round 1's Constraints section), shaped the same way but living in tmux-conductor's own SQLite DB.
- **A catalog is agent-fleet metadata, not a routing decision-maker** — building it does not, by itself, answer "who decides." It makes round 1's Option A (tag-match precedence) meaningfully more useful (real roles instead of ad hoc tags) and makes any future Option B/orchestrator's job easier (structured descriptions to match against instead of raw task text), but it is valuable and shippable independent of either.
- **The conversational-authority failure axis (Finding 3) argues against ever letting a routing mechanism — deterministic or LLM — call anything beyond `POST /queue/:agent`.** This was already round 1's design; this round's contribution is evidence for *why*, which should be treated as a hard constraint in any future implementation, not a nice-to-have.
- **Coding-specific cost figures for orchestrator-worker dispatch remain unfound** (assumption #5 above) — any future decision comparing a catalog-only approach to one with an added LLM router should not import chat/research-agent token multipliers as if they were validated for this workload; flag them as the same imported estimate round 1 already used, not new evidence.

## Recommendation (Extends Round 1–2, Does Not Reverse Them)

Round 1's sequencing ("Ship A now; add B only where A demonstrably falls short; defer C") and round 2's addition ("add Shape D for the no-suitable-agent case") both still stand. This round's addition is a **layer underneath both**, not a fourth competing option:

1. **Build the Specialized-Agent Catalog (Layer G) as part of, or immediately before, round 1's Option A.** Concretely: add `role` and `description` nullable columns to `agents` (can be the same migration as round 1's proposed `tags` column); backfill `role` from the existing `<project>-<role>-<n>` naming convention where it parses cleanly (Finding 4), leave it null elsewhere rather than guessing; surface both via a small addition to the existing `GET /agents` response (no new endpoint needed) so the dashboard's "Add Agent"/edit flows can show and set them like any other field.
2. **Keep every router — today's SQL precedence, round 1's tag-match tier, and any future orchestrator — scoped to `POST /queue/:agent` only, never direct pane control**, per Finding 3's evidence that this is the specific architectural guard against the "subagent takes over" failure class, not just a blast-radius nicety.
3. **If/when round 1's Option B (LLM router) or round 2's Shape D (ephemeral worker) is eventually built, have it consult Layer G's `description` field the way Claude Code's own orchestrator consults `.claude/agents/*.md` descriptions (Finding 2)** — reusing a pattern already proven at the one-layer-up scale, rather than inventing a bespoke matching scheme.
4. **Do not treat this round's findings as grounds to build a fleet-wide "Orchestrator Agent" sooner than rounds 1–2 already recommended.** If anything, Findings 1, 3, and 5 argue for being more conservative than round 1 was: build the catalog, prove it insufficient, *then* add a decision-maker — and when you do, make it call agents strictly as tools (Finding 3), never as conversational peers.

Risks and mitigations:
- **Backfilling `role` from existing agent names could mis-parse ad hoc/copy-cloned names** (`bootstrap-bootstrap-1-copy-2-copy`) — treat backfill as best-effort and nullable, never block agent creation on having a parsed role.
- **A catalog with no consumer risks becoming stale metadata nobody reads** — mitigate by wiring it into round 1's Option A precedence tier immediately (Recommendation step 1 pairs it with a real consumer from day one) rather than shipping it as a standalone dashboard field with no routing effect.
