# Research Round 2: Alternative Shapes for the Orchestrator Agent

> Builds on [index.md](index.md); this update does not repeat round 1's findings on tmux-conductor's current mechanical dispatch or the general orchestrator-worker/supervisor literature — those still stand. This round exists because round 1 quietly assumed the new orchestrator agent would be *a smarter router bolted onto tmux-conductor's existing persistent-pane-plus-SQL-queue shape*. Prompted explicitly to stop assuming the architecture stays the same, this round searched for prior art in the one niche round 1 missed entirely — tools purpose-built to orchestrate fleets of *coding* CLI agents — and found an established ecosystem whose dominant shape is structurally different from round 1's recommendation.

## Assumptions Identified From Round 1

1. Scoped "orchestrator" narrowly to tmux-conductor's SQL task queue, not to live-command routing or fleet-lifecycle management (spawn/kill).
2. Equated "routing tasks" with "assigning queue rows to a pane," never considering that dispatch itself could change shape.
3. Borrowed failure-mode evidence (MAST taxonomy, LangGraph supervisor loops, the "escalate past 5-8 agents" heuristic) from chat/customer-support/research multi-agent systems, then applied it to a coding-agent fleet without checking whether coding-specific tools see the same numbers.
4. Assumed the fleet stays small (~5-8 agents) from the wiki's active-task count, never checking live `dispatch.jsonl`.
5. Never searched for prior art specifically in "orchestrating fleets of coding CLI agents" as its own tool category, separate from generic multi-agent frameworks (LangGraph/AutoGen/CrewAI).
6. Never checked this session's other available working directories for related prior work.
7. Dismissed a dedicated orchestrator pane largely on token-cost figures (~4-15x) drawn from chat/research agents, not coding-task delegation.
8. Treated routing as single-shot placement into an existing agent, not as decomposition/fan-out or as *spawning a new worker for the task*.
9. **(This round's trigger)** Assumed the orchestrator's own shape and spawn mechanism must match tmux-conductor's current architecture (host-server + persistent named tmux panes + `send-keys`), rather than treating "what shape is this agent, and how does it get spawned" as itself an open question.

This round closes gaps 3, 4, 5, 8, and 9 directly; gap 6 partially (the two sibling working directories were listed but not deeply explored — see Constraints); gaps 1, 2, and 7 are addressed indirectly by the alternative shapes below.

## Research Questions
- Does live usage data support or contradict round 1's "small fleet" assumption?
- Does dedicated prior art already exist for orchestrating fleets of coding CLI agents specifically — and if so, what shape does it take?
- What alternative shapes could tmux-conductor's orchestrator take beyond "smarter router into a persistent pane pool" — specifically ephemeral per-task spawning and protocol-native delegation?
- Given that prior art, does round 1's recommendation still hold, or does it need revising?

## Current State (Codebase) — Update

`logs/dispatch.jsonl` shows a materially larger and more churny fleet than the wiki's active-task count suggested: a single day's tail already contains a double-digit number of distinct agent names (`tmux-conductor-fe-research`, three separate `bootstrap-bootstrap-1*` variants, `cryptwiz-cryptwiz-1-copy`, several `tmux-conductor-tmux-conductor-N` instances, multiple short-lived `uat157-*`/`uat157-edge2` fixture agents, etc.), many clearly disposable (test fixtures, one-off UAT dispatch probes). [S18] This matters for two reasons: round 1's "defer any dedicated orchestration mechanism until past ~5-8 agents" threshold is already crossed in practice, and a nontrivial fraction of that churn is already agents that exist for exactly one task and then presumably get torn down — i.e., tmux-conductor's real usage pattern already leans toward ephemeral, task-scoped agents in places, even though its formal data model (named `agents` rows with persistent skills/checkpoints/worktree) assumes long-lived identity.

## Key Findings

1. **A populated, mature tool category already exists for exactly this problem — orchestrating fleets of coding CLI agents — and it is architecturally distinct from the generic chat/customer-support multi-agent literature round 1 drew on.** Surveys count 9-11+ named tools (Claude Squad, Conductor, Crystal/Nimbalyst, Vibe Kanban, Agent Kanban, Emdash, Baton, Bernstein, Agent Orchestrator) plus a longer curated list (dmux, herdr, ClawTeam, corellis, Fusion, swarm-protocol, subtask, vibe-tree, Traycer, Tortie) — all solving some version of "run/coordinate multiple coding agents against one codebase." [S19, S20]

2. **The dominant shape in this ecosystem is ephemeral worker-per-task, not routing into a persistent pool.** dmux, Claude Squad, Vibe Kanban, Conductor, and Crystal all provision a *fresh* tmux pane plus a *fresh* git worktree and branch together when a task is created, then merge and tear the pane/worktree down when it's done — there is no "pick an existing idle agent" decision at all, because there's no existing agent; one is made for the task. [S23, S19] Upsun's writeup names the coordination role this implies directly: "a central orchestrator that assigns tasks, monitors progress, and coordinates merges... understands task dependencies, schedules work to minimize conflicts" — coordinating *ephemeral* workers, not a static fleet. [S24]

3. **Purpose-built "coordinator" roles already exist on top of that ephemeral-worker substrate, and at least one is nearly identical to what this research was asked to design.** `claude-vibe-squad`'s "Chrono" coordinator routes scoped task packets to role-based specialists across five different model families (Claude/Codex/Gemini/Grok/Kimi), each in its own isolated git worktree, with a rival-family review gate before anything lands — "One tmux session, no server." [S21] This is materially closer prior art than anything cited in round 1: an actual shipped OSS project doing task routing across heterogeneous coding-agent vendors inside a single tmux session, with no separate backend process at all.

4. **The "escalate to hierarchical only past 5-8 agents" heuristic round 1 cited does not hold in this specific niche.** `corellis` is explicitly built as "a multi-agent governance framework... goal decomposition, fleet-wide memory, correction propagation, and approval workflows for **20+ agent fleets**" [S20] — 3-4x the threshold round 1 imported from generic multi-agent research. Combined with finding #1 above (tmux-conductor's own live fleet already exceeds that threshold), this specific heuristic from round 1 should be discounted for this project.

5. **A genuinely different "shape" exists that isn't about persistent-vs-ephemeral at all: decentralizing the routing decision to the agents themselves.** herdr is a single background daemon (not a per-project host-server, not a tmux pane) whose defining feature is that "agents drive herdr through the cli and socket api: they can spawn panes, prompt each other, and wait until another agent is genuinely blocked" [S22] — i.e., there is no central "orchestrator agent" making routing decisions at all; any agent can request a new pane or hand off to a sibling directly. This is structurally closer to Claude Code's own Agent Teams (a teammate can spawn siblings) than to a supervisor/router.

6. **A protocol-native alternative to a bespoke tags column or SQL queue exists and is gaining real cross-vendor traction: A2A (Agent2Agent).** Google-originated, now Linux-Foundation-governed, A2A defines a formal task lifecycle (`submitted → working → input-required → completed/failed/canceled/rejected`) over HTTP/JSON-RPC/SSE, plus a standardized capability-advertisement document (the "Agent Card," published at `/.well-known/agent-card.json`) that a delegating agent reads before routing work to another. [S25, S26] Two details make this specifically relevant to tmux-conductor: its `input-required` task state maps directly onto tmux-conductor's own already-implemented `awaiting` agent status, and AutoGen/CrewAI are already adding A2A compatibility for exactly the cross-framework delegation problem tmux-conductor's "vendor-agnostic" design goal implies. [S27] A2A's own guidance is explicit about *when* this shape is warranted: forcing a stateful, multi-turn, clarifying-question-asking agent into a plain stateless tool-call interface "forces an agent into a stateless tool shape when the agent needs to be a peer" [S28] — which describes tmux-conductor's coding agents (Claude Code, Codex, Aider) precisely.

## Constraints — Update

- **tmux-conductor's data model is built around long-lived, named, addressable agents** (rename, clone, per-agent skills endpoint, checkpoints, dashboard continuity). The ephemeral-worker-per-task shape (finding #2) is not a drop-in addition — it changes what "an agent" *is* in this system, from a persistent identity you dispatch into, to a disposable unit of work that exists only for one task's duration. This is a bigger fork in the road than round 1's "add a tags column" framing implied.
- **None of Claude Code, Codex, or Aider natively speak A2A or expose a socket API** — adopting either the A2A shape (finding #6) or the herdr/decentralized shape (finding #5) requires tmux-conductor to build and maintain a protocol/socket shim per agent vendor, a materially larger lift than round 1's proposed schema change.
- **The sibling working directories available in this session** (`tmux-agent-status`, `claude-code-lsp-enforcement-kit`) were not deeply explored this round — Serena's project-root restriction blocks its tools outside `tmux-conductor`, and a targeted look was out of scope for this pass. If either contains prior experimentation on this exact question, a follow-up pass should check them directly (`cd` a subagent into each, or open them as their own Serena projects).
- **tmux-conductor already has the *primitive* the ephemeral shape needs** — `agents.worktreePath` and the existing checkpoint/stash mechanism (`stashCheckpoint` in `dispatchTaskToAgent`) — but uses it for optional isolation of a persistent agent, not for provision-then-teardown per task. Borrowing dmux's lifecycle-hook model (worktree create → task run → pre-merge → post-merge → cleanup) is more a matter of sequencing existing primitives differently than building new ones.

## Solution Comparison — Alternative Shapes (supersedes round 1's A/B/C framing as the full picture)

| Shape | D. Ephemeral worker-per-task (dmux / Claude Squad / Vibe Kanban model) | E. Protocol-native delegation (A2A) | F. Decentralized, agent-initiated (herdr model) |
|---|---|---|---|
| **Approach** | Task creation provisions a fresh git worktree + branch + tmux pane + agent launch together; completion triggers auto-commit/merge/teardown | Each agent (or a thin per-agent shim) publishes an Agent Card and exposes A2A task-lifecycle endpoints; a coordinator discovers and delegates via the standard, not a bespoke queue | A single lightweight daemon owns pane lifecycle; agents themselves call its CLI/socket API to spawn siblings or hand off, with no central router deciding |
| **Pros** | Proven, purpose-built for coding agents specifically (not borrowed from chat/support); eliminates "which existing pane" question entirely; naturally isolates parallel work | Standardized, vendor-agnostic capability discovery + task lifecycle that already matches tmux-conductor's stated design goal; `input-required` state reuses work already done for `awaiting` detection | Removes the single-router failure mode entirely; matches how Claude Code's own Agent Teams already lets a teammate spawn siblings |
| **Cons** | Changes what "an agent" is in tmux-conductor's data model — breaks the persistent-named-agent identity the dashboard is built around | Biggest lift: no target agent CLI speaks A2A natively; protocol/shim work per vendor; likely overkill for a single-user local tool (A2A is designed for cross-org enterprise delegation) | Decentralizes the audit trail round 1 argued was essential; higher risk of the "everyone/no one owns the task" symptom (round 1, S17) |
| **Complexity** | Medium-High | High | High |
| **Codebase fit** | Partial — `worktreePath`/checkpoint primitives already exist; identity model does not | Conceptually excellent fit (vendor-agnostic is already a stated goal); practically the furthest from current code | Furthest from current host-server-centric architecture |

## Recommendation (Revised)

Round 1's recommendation ("add a `tags` column, extend `popTask` precedence") is not wrong, but it answers a narrower question than the one actually posed. The real first decision is **which shape the orchestrator's *targets* take** — persistent named agents (today's model) vs. ephemeral per-task workers (the ecosystem's dominant model) — because that decision determines what a "routing decision" even means. Recommended path:

1. **Keep round 1's tag-match precedence tier as the router for tasks scoped to existing, named agents** (Shape A from round 1) — it's still correct for the case where a human has already spun up a long-lived agent for a project and wants tasks funneled to it.
2. **Add a second path modeled on dmux's lifecycle** (Shape D) for the case round 1 didn't have an answer for: a task with no existing suitable agent. Instead of leaving it in an unassigned global bucket (round 1's fallback), provision a fresh worktree + tmux pane + agent launch for it, using dmux's hook points (worktree-create → run → pre-merge → post-merge → cleanup) as the reference sequence, and reuse tmux-conductor's own existing `worktreePath`/checkpoint machinery rather than building new primitives.
3. **Do not pursue A2A (Shape E) now** — the protocol fit is real and worth remembering (`relates_to` tmux-conductor's own vendor-agnostic goal, and its `input-required` state already conceptually matches `awaiting`), but building per-vendor shims for Claude Code/Codex/Aider is disproportionate to a single-user local tool. Revisit only if genuine cross-machine or cross-user agent delegation becomes a real requirement — which prior remote-access research already flagged as intentionally out of scope.
4. **Do not pursue full decentralization (Shape F) now**, but borrow its narrower idea: let a *running* agent request a new sibling pane/worktree directly (closer to how Claude Code's own Agent Teams already work) as an addition to, not a replacement for, centralized routing observability.
5. **Treat this as a decision, not a task.** Given the design space just got materially larger (four candidate shapes, not three tweaks to one shape), `/decision-create` comparing "extend the current persistent-fleet router" vs. "add an ephemeral-worker-per-task path" is the right next step before any implementation task is filed — round 1's suggested `/task-add` for the tags column alone is still fine to file as a small, independent first slice, but it should no longer be presented as "the" first step for the whole orchestrator question.
