# Research: BUG-0001 background-agent detection — payload shape and implementation options

> Current official docs confirm `agent_needs_input` fires **only** when a background agent is genuinely blocked on a decision — never as a general "still running" ping — which means BUG-0001's existing sentinel fix structurally cannot protect an autonomous background sub-agent that never asks for input (very likely what the original incident's `Agent(UAT auto TASK-109)` was doing). The docs do **not** confirm a per-agent correlator field for the Notification payload. But they surface a previously-unknown, better-targeted signal: the interactive session's prompt-footer hint (`← 2 agents` / `← for agents` / `← 2 done`), which is documented to distinguish "N agents need input" from "agents active, none need input" — exactly the missing case. Its exact behavior with **zero** background agents ever dispatched is not fully pinned down by docs, so a live check (cheap — no global config needed, unlike payload capture) is the one remaining gap before implementing. Recommendation: build the pane-text heuristic (mirroring `AWAITING_PATTERN`) using this footer hint as the primary mechanism, keep the existing hook-based sentinel as a secondary defense-in-depth signal for the narrower case it already covers correctly, and defer the correlator-focused live payload capture (global hook install) since it doesn't address the actual gap.

## Research Questions
- What is the full documented JSON payload/schema for the `Notification` hook, and does it include a per-agent correlator (`agent_id`, `task_id`, `job_id`, or similar) for `agent_needs_input`/`agent_completed` specifically?
- Does `agent_needs_input` fire as a general "still outstanding" signal or only when a decision is genuinely needed? Does `agent_completed` fire reliably for every background-agent lifecycle end (success and failure)?
- What is the actual, current UI text Claude Code shows for "background agent(s) active," and how stable/precise is it as a pattern-matching target?
- How would each option (pane-text heuristic vs. live payload capture) concretely integrate into this codebase's existing status-detection architecture?
- Given the findings, is one option sufficient, or is a hybrid the right call?

## Current State (Codebase)

- `hooks/on-notification.js` — writes a sentinel file under `$STATE_DIR/<agent>.pending-agents/<timestamp>-<random>` on `agent_needs_input`, removes the oldest (FIFO, no correlator) on `agent_completed`; every other `notification_type` is a no-op (logged only). Explicitly documents (in its own header comment) that it was built without a confirmed correlator, and that this is a known limitation.
- `host-server/pendingAgents.ts::hasPendingBackgroundAgents(stateDir, windowName, staleMs)` — true if any sentinel in that directory is fresher than `staleMs` (default `PENDING_AGENT_STALE_S` = 3600s); stale sentinels are logged and ignored so a missed `agent_completed` can't wedge the queue forever.
- Two dispatch call sites in `host-server/index.ts` gate on `!hasPendingBackgroundAgents(...)`: the `POST /api/tasks` immediate-enqueue fast path (~line 925) and `pollAndDiff`'s idle-transition trigger (~line 2425) — both hold dispatch while a fresh sentinel exists.
- `conductor.conf`'s `AWAITING_PATTERN` (`'(\?\s*$|\?\s+[A-Za-z]+(/[A-Za-z]+)+\s*$|\[Y/n\]|\[y/N\]|>\s*$|Enter to (select|confirm|submit)|Esc to (cancel|go back)|ctrl.g to edit|shift.tab to approve)'`) is the existing precedent for exactly this class of problem: Claude Code exposes no clean hook for "waiting on a human," so this codebase already detects it via pane-text matching instead. Two independent consumers apply it identically: `scripts/monitor.sh::is_idle()` (matches against the pane's last non-blank lines via `grep -qE`, only checked while state is `busy`, writes `awaiting` to the state file) and `host-server/state.ts::detectAgentStatus()` (`matchesAwaiting()`, matched against the last 8 non-blank lines, read-only re-evaluation every 2s for dashboard responsiveness, not gated on state-file age). Both are driven off the single conf-sourced pattern — no duplicated hardcoded copy.
- `raw/research/stop-hook-subagent-detection/index.md` (2026-08-15) is the prior research this fix was built from — it already established the `Stop` hook payload doesn't help, discovered the two `Notification` types, and explicitly flagged (as *inference*, not confirmed) that the firing semantics and correlator were unknown. This report resolves one of those two questions and adds a new candidate signal neither prior research nor the original implementation considered.

## Key Findings

- **`agent_needs_input` fires only when a background agent needs a decision — confirmed, not inferred.** Current docs: "While agent view is open, Claude Code also sends a notification through your configured terminal notification channel when a local background session **starts needing your input, finishes, or fails**... fire the `Notification` hook with the `agent_needs_input` or `agent_completed` type." [S1] This directly resolves the open question from the prior research: it is NOT a general "still outstanding" heartbeat. A background agent that runs to completion without ever needing input never fires it.
- **`agent_completed` fires on both success and failure**, per the same sentence ("finishes, or fails") [S1] — the existing FIFO-clear-on-`agent_completed` logic is directionally sound as a *clear* signal; the gap is entirely on the *set* side.
- **No documented per-agent correlator for Notification payloads.** The hooks reference's "Common input fields" table lists `session_id`, `prompt_id`, `transcript_path`, `cwd`, `permission_mode`, `effort`, `hook_event_name` for every hook event [S2]. A separate `agent_id`/`agent_type` pair exists, but is explicitly scoped to "when running with `--agent` or inside a subagent" — i.e. it identifies whether *the process the hook fires inside* is itself a subagent, not which background job a `Notification` event refers to [S2][S3]. Background sessions do have their own identifiers — short IDs under `~/.claude/jobs/<id>` and a full `sessionId` [S3] — but no source found confirms these are exposed on the `Notification` payload specifically. A dedicated worked example for the Notification event's own JSON shape was not found in three fetch attempts (the docs page appears to truncate before that section in automated fetches) — this specific gap remains genuinely unresolved by documentation.
- **New finding, not in the prior research: the interactive prompt footer is a documented, more precisely-scoped signal.** "Inside a regular `claude` session, the prompt footer's `←` hint counts the background agents that are waiting on you, such as `← 2 agents`, and returns to `← for agents` when none need input. Counts above 99 show as `99+`. The count refreshes about every ten seconds while the terminal is focused... when a background session finishes while none need your input it briefly shows the number completed, such as `← 2 done`." [S3] Three distinct, documented states: `← N agents` (N need input — the case the existing hook-based fix already covers), `← for agents` (agents active, **none currently need input** — the exact missing case), `← N done` (transient, N completed while none needed input).
- **The one thing documentation does not resolve**: whether `← for agents` is shown *only* when at least one background agent exists (active or recently completed), or persists as a baseline UI element even with zero background agents ever dispatched in the session. Three separate fetch attempts at the same page produced consistent quotes of the same paragraph but no explicit statement of the zero-agents case. This is the one remaining gap before a pane-text pattern can be written safely — a wrong assumption here (matching when zero agents exist) would be *actively harmful*, not just ineffective: it would permanently block dispatch, which is worse than the bug it's meant to fix.
- **The gap is a known, real-world pain point beyond this codebase.** GitHub issue `anthropics/claude-code#45781` ("Add BackgroundTasksIdle notification event," closed as not-planned) describes the identical structural problem from a different angle: a user launching many parallel background agents gets notification noise they can't distinguish from genuine completion, because Claude Code's current signals don't cleanly separate "agents active, nothing needed" from "genuinely idle." [S4] No payload details in that issue, but it corroborates that this is a real, acknowledged product gap, not a misunderstanding on this repo's part.
- **No "started" event exists**, reconfirmed against the full current `Notification` matcher-type list: `permission_prompt`, `idle_prompt`, `auth_success`, `elicitation_dialog`, `elicitation_url_dialog`, `elicitation_complete`, `elicitation_response`, `agent_needs_input`, `agent_completed`, `quota_auto_resume_fired`, `quota_auto_resume_stale`, `quota_auto_resume_disabled` [S2]. There is still no documented way to seed a sentinel at background-agent-dispatch time via any Notification type.

## Constraints

- A wrong pane-text pattern is worse than no pattern: false-positive matches on an idle/no-agent pane would permanently block dispatch (bounded only by whatever staleness fallback is added), a strictly worse failure mode than BUG-0001's original false-idle dispatch.
- Any solution must integrate at the two existing `hasPendingBackgroundAgents(...)` gate call sites without duplicating them — `host-server/index.ts` lines ~925 and ~2425.
- Must not resurrect the `done`/`working`/`wait`/`dispatching` 4-state vocabulary TASK-009 deliberately collapsed (same constraint the original fix already honored).
- Global Claude Code config changes (`~/.claude/settings.json`) are out of scope for autonomous/unattended work in this repo per this session's own established caution — any option requiring that needs explicit user go-ahead.

## Solution Comparison

| Criteria | Option 1 — Pane-text heuristic (`← for agents`) | Option 2 — Live Notification payload capture |
|---|---|---|
| **Approach** | New pattern (e.g. `BACKGROUND_AGENT_ACTIVE_PATTERN`) matched against the pane's captured tail, mirroring `AWAITING_PATTERN`'s existing mechanism in both `monitor.sh` and `state.ts` | Install this repo's hooks into `~/.claude/settings.json`, dispatch a real background agent, inspect `notification-debug.jsonl` for the actual payload shape |
| **Addresses the actual gap?** | Yes — directly, per documented footer semantics | No — even with a confirmed payload, there's still no "started" event; capture would only refine the correlator question for the narrower "needs input" sub-case that already works |
| **Blast radius** | Repo-local only | Machine-wide: affects every Claude Code session on the machine, not just this repo |
| **What's still unconfirmed** | Whether `← for agents` appears with zero background agents ever dispatched (needs one live look at a real footer, no config change required) | Whether a correlator field exists at all (three fetches found none documented) |
| **Complexity** | Low — one new conf pattern + a few-line integration at two existing call sites, same shape as `AWAITING_PATTERN` | Medium — global hook registration, then a real background-agent dispatch to observe, then possibly redesigning the FIFO scheme around whatever's found |
| **Risk if wrong** | High if unverified (see Constraints) — but easily verified first with one live look, no config change | Low technically, but may spend the machine-wide-config cost and still not resolve the core problem |
| **Codebase fit** | Excellent — extends an established, already-trusted pattern (`AWAITING_PATTERN`) with the same staleness-fallback philosophy this codebase already uses everywhere | Fine, but net-new infrastructure (global hook install) with no existing precedent in this repo |

## Recommendation

**Build Option 1 as the primary mechanism; keep the existing hook-based sentinel as a secondary signal; defer Option 2.**

Implementation outline for Option 1:
1. **Resolve the one open question first, cheaply**: get one real look at a live Claude Code session's footer while a background agent is running vs. idle-with-zero-agents-ever-dispatched vs. idle-with-a-just-completed-agent. This does **not** require installing anything — either observe it directly during normal use, or dispatch a background agent inside one real `tmux-conductor`-hosted agent pane and `tmux capture-pane` it (this repo already does exactly this kind of live tmux verification for other bugs, e.g. `scripts/verify-teardown-window-mapping.sh`). No global config touched either way.
2. **Add `BACKGROUND_AGENT_ACTIVE_PATTERN`** to `conductor.conf`, following `AWAITING_PATTERN`'s exact precedent (comment explaining the false-positive risk it must avoid, single conf-sourced value, no duplicated hardcoded copy). Candidate starting pattern once confirmed: something anchored on `for agents` as the last non-blank line (mirroring `AWAITING_PATTERN`'s end-of-line anchoring for its own false-positive avoidance), explicitly excluding a plain idle prompt.
3. **Wire it into `host-server/state.ts`** alongside `matchesAwaiting()` — a `matchesBackgroundAgentActive()` check against the same captured tail — and into `hasPendingBackgroundAgents()`'s effective gate (either fold into that function's return value by passing the pane tail in, or OR the two conditions at each of the two `host-server/index.ts` call sites). Both existing call sites already have the pane/window context needed.
4. **Keep `hooks/on-notification.js` + `pendingAgents.ts` as-is** — they're still correct for the "agent needs input" sub-case, cost nothing extra to retain, and fire faster/more precisely than a 2s-poll pane-text check for that case specifically.
5. **Regression test**: this repo has an established pattern for exactly this kind of thing (`scripts/verify-*.sh` driving a real process end-to-end against a scratch fixture) — a live test could dispatch a real background agent inside a scratch tmux pane and assert the new pattern matches while active and stops matching once `agent_completed`/completion is observed, mirroring `scripts/verify-teardown-window-mapping.sh`'s shape.

**Risks and mitigations**:
- *Risk*: footer text changes with future Claude Code versions. *Mitigation*: same accepted tradeoff `AWAITING_PATTERN` already lives with — bounded by the same kind of staleness fallback, and loudly logged if it stops matching (mirrors the existing `stalled` pattern).
- *Risk*: the zero-agents case does turn out to render `← for agents` too. *Mitigation*: this is exactly why step 1 (one cheap live look) comes before step 2 (writing the pattern) — don't ship a pattern until this is confirmed one way or the other.

**When Option 2 becomes worth it**: only if, after Option 1 ships, concurrent-background-agent mis-clearing (the FIFO scheme's known weakness) turns out to matter in practice — at that point, live payload capture is worth the machine-wide config cost specifically to hunt for a correlator, with the user's explicit go-ahead.

## Next Steps
- Do the one cheap live footer check (step 1 above) — no `/task-add` needed yet, this is a quick verification, not a build task.
- Once confirmed: `/task-add` for the `BACKGROUND_AGENT_ACTIVE_PATTERN` implementation (steps 2-5 above), scoped to `conductor.conf`, `host-server/state.ts`, `host-server/index.ts`, and a new `scripts/verify-*.sh` regression test.
- No further documentation research needed on the correlator question — it's now confirmed unanswerable from docs alone (three independent fetch attempts); only a live payload capture (Option 2, deferred) could resolve it, and it wouldn't resolve the primary gap anyway.
