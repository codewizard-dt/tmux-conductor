# Research: Host-Wide Claude Code Agent Identification, Categorization, and Control

> **Identification/categorization: yes, reliably** — `claude agents --json` plus a TTY-to-tmux-pane correlation (empirically verified live, twice) gives an exact three-way split (tmux-hosted-with-known-pane / plain-terminal / headless-background) on top of the documented `kind`/`cwd`/`status` fields. **Control: it depends entirely on that category.** A tmux-hosted session (whoever spawned it) is trivially controllable via ordinary `tmux send-keys` — no different from tmux-conductor's own agents. A headless background session has a real CLI management surface (`attach`/`stop`/`logs`/`respawn`/`rm`) but **no scriptable way to inject text** — `attach` is an interactive terminal reattachment only. A plain-terminal interactive session (not in any tmux pane) has **no automatable control path at all**. Claude Code's own cross-session messaging (`SendMessage`/`ListAgents`, the tools this research session itself used) is real, documented, and Unix-socket-based, but it's invocable only from *inside* a running Claude Code process — not from an arbitrary external process like tmux-conductor's host-server — without reverse-engineering an undocumented wire protocol, which is not recommended.

## Research Questions
- Can a Claude Code session's tmux location (if any) be identified reliably from outside, without ambiguity, for a session tmux-conductor didn't spawn?
- Can such sessions be categorized (conductor-managed vs. ad-hoc; tmux-hosted vs. plain-terminal vs. headless; interactive vs. background; which project) with signals that hold up under a live, messy, multi-session environment?
- Is `claude attach`/the agent-view CLI control surface actually scriptable, or interactive-only?
- What is the real transport and constraints behind Claude Code's cross-session messaging (`SendMessage`/`ListAgents`), and can a non-Claude-Code process (like tmux-conductor's host-server) use it directly?
- Given all of the above, what's the practical, supported way (if any) for tmux-conductor to send a command to a session it doesn't manage?

## Current State (Codebase)

Builds on [the prior research round](../detect-active-claude-code-sessions-kanban/index.md) — that established `claude agents --json` as the base discovery mechanism and that tmux-conductor's own registered-agent kanban has no discovery step today. This round goes one level deeper: given a session `claude agents --json` reports, can it be *placed* (which pane, if any) and *acted on*.

## Key Findings

**F1 — TTY-to-tmux-pane correlation is real and empirically verified, not just plausible.** A session's controlling terminal device (`ps -o tty= -p <pid>`) can be cross-referenced against `tmux list-panes -a -F "#{pane_tty} #{session_name}:#{window_index}.#{pane_index}"` — run with `-a` so it covers **every** tmux session on the server, not just tmux-conductor's own. Verified live twice: pid 88840 (`ttys006`) matched exactly to pane `conductor:1.0`; pid 89060 (`ttys009`) matched exactly to pane `conductor:4.0` [S1]. A pid whose tty exists but isn't in the pane list is a plain (non-tmux) terminal window/tab. A pid with no controlling tty at all (macOS shows `??`) is a genuinely headless/daemon-managed session — confirmed on the one live session whose `claude agents --json` `kind` was `background` (pid 31343): its tty was `??`, while every currently-alive `kind:"interactive"` session had a real tty [S1]. This gives a clean three-way categorization with no ambiguity, layered on top of the already-documented `cwd`/`kind`/`status` fields from the prior research round.

**F2 — A live mistake, caught before it was reported as a finding.** Three pids (88808/88988/89064) initially looked like "detached orphans surviving a closed tmux window" because `ps -o tty= -p <pid>` printed nothing for them. Re-checked with `kill -0 <pid>` first: **all three had simply exited** between the earlier scan and this one — `ps -o tty=` returns an empty string both for "process has no controlling terminal" and "no such process," and the first check conflated the two. There is no evidence of daemon-orphaned survivors from closed tmux windows; the tmux window and the underlying `claude` process died together, as expected. **Lesson for implementation: always gate on `kill -0`/process-liveness before interpreting an empty tty field.**

**F3 — `claude attach`/`logs`/`stop` are documented, real, but not a command-injection channel.** Full `--help` text confirmed: `claude attach <id>` — "Open the background session in this terminal[.] ← returns to agent view, Ctrl+Z drops back to your shell. The session keeps running either way" (interactive reattachment for a human, no flag to pipe text in); `claude logs <id>` — read-only recent output; `claude stop <id>` — stop it, resumable later via `attach` [S2]. **This corrects a claim from the prior research round** — background sessions have a real *management* surface (stop/logs/respawn/rm), not a *scripted command-injection* surface. Nothing in the documented CLI lets an external script feed text into a running session, background or interactive.

**F4 — tmux-hosted sessions are trivially controllable regardless of who spawned them.** tmux doesn't distinguish "a pane tmux-conductor created" from "a pane the user opened by hand" — `tmux send-keys -t <session>:<window>.<pane>` works identically either way. Combined with F1's pane-location lookup, **this is the single most practical control mechanism available today** for any ad-hoc session that happens to live in a tmux pane tmux-conductor's host process can reach (i.e., on a tmux server/socket it has access to) *(inference from tmux's own documented behavior plus F1 — no primary source states this explicitly, since it follows directly from how `send-keys` addressing works)*.

**F5 — Cross-session messaging (`SendMessage`/`ListAgents`) is a real, documented, first-party feature — not an internal-only mechanism.** Official docs (`code.claude.com/docs/en/cross-session-messaging`, confirmed via Context7 and independently quoted verbatim by a Brave Search snippet of that same URL): "Claude Code binds an inbox socket for each session with cross-session messaging enabled, where other sessions on the machine deliver messages. The socket is a Unix domain socket on macOS and Linux... and a named pipe on native Windows" [S3]. Requires Claude Code v2.1.224+ (stated twice in the official Context7 doc excerpt, for both `ListAgents` and `SendMessage`) [S3]. **Directly confirmed on this machine**: `~/.claude/sessions/<pid>.json`'s `messagingSocketPath` field points at `/tmp/cc-socks/<pid>.sock`, and a Python `stat.S_ISSOCK` check confirmed all 12 checked paths are real, currently-live Unix domain sockets [S4] — i.e., the exact "register themselves in files on disk and bind a local inbox socket there" mechanism the docs describe [S3], caught in the act on a real system.

**F6 — This channel is not something an external process can safely speak directly.** The tool-level behavior, settings, and version gate are documented; the literal wire protocol spoken over `/tmp/cc-socks/<pid>.sock` is not. `SendMessage`/`ListAgents` are agent-harness tools a *running Claude Code process* calls — there is no `claude <verb>` CLI subcommand to trigger a delivery from an external script (the full top-level command list has no `message`/`send` verb) [S2]. Reverse-engineering the socket's byte format to let tmux-conductor's host-server (a plain Node/Fastify process) speak it directly would be unsupported and version-fragile — not recommended.

**F7 — A background/non-interactive session can still receive a cross-session message, with real caveats.** Multiple independent, mutually-consistent sources state a `claude -p` (print-mode/non-interactive) session binds the same inbox socket as an interactive one and can receive messages [S5, S6] — but "it can't display the approval dialog, so a held message stays held unless you set `crossSessionInbound: 'accept'`" in its settings [S6]. The official `crossSessionInbound` setting (`accept`/`hold`/`refuse`, requires v2.1.224+) governs this per-receiver [S3, via settings-reference page cited in the same Context7 result]. Delivery is also rate-limited (repeated/identical messages throttled) and capped (a 50-message unread queue per multiple sources, a separate 100-message held-message cap per another) [S6, S7] — this is advisory text delivered "between tool calls or starts a fresh turn if idle" [S8], never authoritative — the receiving Claude decides what, if anything, to do with it, exactly like any other input.

**F8 — A legitimate (if heavier) indirect path exists: let an actual `claude` process do the sending.** Since the only supported way to trigger a `SendMessage` delivery is from inside a running Claude Code process, tmux-conductor's host-server *could* shell out to a throwaway `claude -p "Use SendMessage to tell <session-name> to ..."` invocation, which is a real Claude Code process that can legitimately call `ListAgents`/`SendMessage` on the caller's behalf *(inference — combines F5/F6/F7's documented facts; no source describes this exact pattern, but every building block is independently confirmed)*. This costs a full model turn (tokens, latency, and the receiver's own `crossSessionInbound` policy still applies) and only ever delivers advisory text — not a guaranteed command execution — so it's a fundamentally different capability than `tmux send-keys`, not a drop-in replacement for it.

## Constraints

- `tmux send-keys` (F4) only reaches panes on a tmux server/socket the host-server process can actually access — a session in a different tmux server socket, inside a container, or over SSH to a different host is out of reach regardless of how well it's identified.
- Plain-terminal interactive sessions (real tty, not a tmux pane) have **no automatable control path** found in this research — genuinely read-only from outside.
- Cross-session messaging requires Claude Code v2.1.224+ on the target session, is opt-out-able (`crossSessionInbound: "refuse"`, or denying `SendMessage`/`ListAgents` via permission rules), and only reaches sessions visible on the **same filesystem** — a session inside a container or across certain platform boundaries (WSL2 vs. native Windows) is unreachable even when otherwise "on the same machine" [S6, S7].
- Any message delivered via `SendMessage` (directly or via the F8 relay pattern) is advisory input the receiving Claude interprets — never a guaranteed, synchronous command execution the way `tmux send-keys` is.
- `~/.claude/sessions/<pid>.json` and its `messagingSocketPath` remain an undocumented internal format (per the prior research round) — safe to *read* for identification purposes, not safe to build a *write* path on top of.

## Solution Comparison

| Session category (from F1's identification) | Identify reliably? | Send a command? | Mechanism | Caveats |
|---|---|---|---|---|
| **tmux-hosted** (tty matches a live pane, any tmux session) | Yes — exact `session:window.pane` via tty cross-reference | **Yes** | `tmux send-keys -t <target>` | Identical to controlling tmux-conductor's own agents; only reaches panes on an accessible tmux server |
| **Headless/background** (`kind:"background"`, no tty, has an `id`) | Yes — `claude agents --json`'s `kind`/`id`/`state` | **No scriptable path** | `claude attach <id>` (interactive-only), `claude stop <id>`, `claude logs <id>` (read-only) | No documented way to pipe text in; a human can `attach` and type, a script cannot |
| **Plain-terminal interactive** (real tty, not a tmux pane) | Yes — has a tty absent from `tmux list-panes -a` | **No path found** | — | Genuinely uncontrollable from outside without OS-level UI automation (out of scope for this research) |
| **Any of the above, if it's itself a live Claude Code session** | N/A (orthogonal capability) | **Indirectly, as advisory text** | Relay via a throwaway `claude -p "...SendMessage..."` process (F8) | Not command execution; subject to receiver's `crossSessionInbound` policy, rate limits, and costs a real model turn |

## Recommendation

**For identification/categorization**: extend the prior round's `claude agents --json`-based detection with the tty-to-tmux-pane cross-reference from F1. Concretely: for each session in `claude agents --json`'s output, look up `ps -o tty= -p <pid>` (skip entries with no `pid`, i.e. background sessions past process exit), and check that tty against `tmux list-panes -a -F "#{pane_tty} #{session_name}:#{window_index}.#{pane_index}"`. This yields, per session: exact tmux location (if any), `interactive`/`background` kind (from the JSON), and — by matching `cwd` against the registered `agents` table's `workdir` — conductor-managed vs. ad-hoc. No new dependency beyond `tmux` and `ps`, both already required by this project.

**For control**: implement `tmux send-keys` dispatch for any *detected, tmux-hosted* session exactly as tmux-conductor already does for its own agents (F4) — this is real, immediate, and needs no new mechanism. Do **not** attempt to build control for headless-background or plain-terminal sessions; document them as detect-only in the dashboard (matches the read-only recommendation from the prior research round, now confirmed rather than assumed). Do **not** attempt to speak the cross-session-messaging Unix socket protocol directly from host-server (F6) — it's undocumented and would be unsupported. If a lighter-weight "nudge a background or plain-terminal session" capability is ever wanted, the F8 relay pattern (shell out to a throwaway `claude -p` that calls `SendMessage` itself) is the only supported route, and should be scoped as a distinct, clearly-labeled "send an advisory message" feature — never described to a user as "run this command in that session."

**Risks and mitigations:**
- Always gate tty checks on `kill -0`/liveness first (F2) — an empty tty field is ambiguous between "no controlling terminal" and "process is gone" and getting this backwards produces false "orphaned session" alarms.
- `tmux send-keys` dispatch into a session tmux-conductor didn't spawn has no state-file/hook feedback loop (that session's Claude Code hooks, if installed, write to whatever `STATE_DIR` *that* session was launched with, not tmux-conductor's) — so idle/busy detection for an adopted ad-hoc session would need to fall back to `claude agents --json`'s own `status`/`state` field, not tmux-conductor's existing hook-based state files.
- Cross-session-messaging behavior is gated by a version check (v2.1.224+) and by the receiver's own settings — any future relay feature (F8) must handle "the target doesn't support it" and "the target refused/held it" as normal, expected outcomes, not errors.
