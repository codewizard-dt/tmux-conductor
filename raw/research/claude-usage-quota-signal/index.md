# Research: A real usage/quota signal for tmux-conductor's USAGE_CHECK_CMD

> **No reliable, non-interactively-scriptable signal exists today.** `USAGE_CHECK_CMD` was meant to detect whether the operator's Claude subscription (Max/Pro, used via Claude Code CLI) is near or has hit its usage limit, before dispatching another task. That specific signal — subscription-level, session/weekly usage-limit status — is not exposed anywhere a shell script can read it non-interactively. The closest official surface, Claude Code's `/usage` slash command, only works typed inside a live interactive session, and even then is a locally-computed estimate, not authoritative server truth. An open issue on the `anthropics/claude-code` repo itself (#33820) confirms Claude Code does not expose any rate-limit/quota data to hooks or status-line scripts. `USAGE_CHECK_CMD='true'` (the fix already deployed by the team, effectively "no automated checking") is therefore the correct current state, not a stopgap that needs replacing today.

## Research Questions

1. Do Claude Code's local session JSONL transcripts (already parsed by this repo's `host-server/usage.ts` / `host-server/context.ts` for token counts and context-window %) carry enough information to derive a usage-limit/rate-limit signal, or only raw token consumption with no cap/limit reference?
2. Does an official Anthropic API usage/billing/rate-limit endpoint exist that could be queried directly (organization usage API, admin API, rate-limit response headers)?
3. Does `claude auth status` or `claude doctor` expose anything usage-related beyond subscription tier?
4. Does Claude Code expose any OTel/telemetry export that could report usage-limit-approaching signals?
5. Does Claude Code's interactive session have any documented internal signal for "approaching usage limit" observable from outside the session?

## Current State (Codebase)

- `host-server/usage.ts` (`extractUsageDeltas`, `getUsageSessionStart`) already parses Claude Code transcript JSONL for per-request token deltas (input/output/cache tokens) — this is raw **consumption**, not a cap or remaining-quota figure.
- `host-server/context.ts` parses the same transcripts for context-window fill %, a completely separate concept (per-conversation token budget, not account-level usage limit).
- `host-server/pricing.ts` / `usage-store.ts` compute a local `cost_usd` from those token counts against a static pricing table — again, spend estimation, not a quota/limit signal.
- `conductor.conf`'s `USAGE_CHECK_CMD` was `claude usage 2>/dev/null | grep -qi "extra usage" && exit 1 || exit 0` — `claude usage` is not a real CLI subcommand (confirmed via `claude --help`, no `usage` command exists), so this fired a full agentic Claude Code turn instead of checking anything. The team has already fixed this to `USAGE_CHECK_CMD='true'` (see [[conductor-usage-check-and-detection-bugs]] internal note) — there is currently **no** automated usage checking in the running system, which is the honest and safe state given finding below.

## Key Findings

- **`anthropic-ratelimit-*` HTTP response headers exist on every Anthropic Messages API response** (not just 429s) — `anthropic-ratelimit-requests-limit/remaining/reset`, `anthropic-ratelimit-tokens-limit/remaining/reset` (input/output split) [S1][S4][S5]. These describe **API-key-based** rate limits (RPM/TPM by Build Tier) under pay-as-you-go billing — a completely different metering model from a Claude Max/Pro **subscription**'s session/weekly usage allowance. Claude Code CLI when signed in via a Pro/Max subscription authenticates via OAuth, not a metered API key, so these headers (even if Claude Code's own internal HTTP client sees them) are not the subscription-quota signal tmux-conductor needs.
- **Claude Code does NOT expose any usage/quota signal to external scripts today — confirmed by an open issue on the vendor's own repo.** `anthropics/claude-code#33820`, "Expose API rate-limit response headers to hooks and status line scripts," states plainly: *"The Anthropic API returns detailed rate-limit headers on every response ... but Claude Code does not expose these to hooks or status line scripts"* [S5]. This is the single most decisive piece of evidence for this research: the feature tmux-conductor's `USAGE_CHECK_CMD` was trying to approximate does not exist as a public, scriptable Claude Code capability as of this research date.
- **`/usage` is a real Claude Code feature — but it is interactive-only, not CLI-scriptable, and self-described as a local estimate.** Multiple independent sources confirm `/usage` is a **slash command typed inside a running interactive Claude Code session** (not a `claude usage` shell invocation), showing session (5-hour rolling window) and weekly usage bars plus a per-skill/subagent/MCP-server breakdown [S2][S3][S7]. Crucially, one source quotes Claude Code's own in-product disclaimer on `/usage`: *"based on local sessions on this machine, does not include other devices or claude.ai"* [S6] — meaning even the official in-session view is a locally-computed estimate, not authoritative server-side truth. There is no documented `claude usage` (or equivalent) non-interactive CLI subcommand or flag that surfaces the same data outside a live session — consistent with the direct verification already done this session (`claude --help`'s full command list has no `usage` entry).
- **Claude subscription usage is a shared, cross-surface pool with two clocks, not a simple token counter.** Pro/Max/Team plans meter a 5-hour rolling session window plus a weekly cap (Max/Team also split the weekly cap across "all models" and "Sonnet-only") [S3][S6]; usage is shared across claude.ai, Claude Desktop, and Claude Code — "all activity in both tools counts against the same usage limits" [S6]. Anthropic does not publish the exact token-to-quota conversion formula (it varies by model, effort level, and other factors) [S3] — so even a perfect local transcript parse cannot deterministically reconstruct "how much of the plan's budget is left" without that formula.
- **`claude auth status` and `claude doctor` carry no usage data** (directly verified this session: `auth status` returns `{loggedIn, authMethod, apiProvider, email, orgId, orgName, subscriptionType}` — tier only, no quota; `doctor` is an installation-health check with no usage-related flags in `--help`).
- **No documented Admin/Organization Usage API surfaced for this** — the `claude-api` skill (loaded as the authoritative source per instruction) mentions "Admin API endpoints" only once, in passing, as an example of a different pagination cursor scheme (`after_id`/`before_id` vs `page`/`next_page`) — with no usage/cost-query endpoint documented or referenced anywhere in the skill's cached content. This does not rule out an enterprise-tier organization spend-reporting endpoint existing outside the skill's scope, but (a) the skill is scoped to building *applications against* the Claude API, not to querying a Max/Pro *subscription's* usage, and (b) even an org-level API-spend endpoint would report metered API billing, not a personal Claude Code subscription's session/weekly quota — a different product entirely. *(This point is an inference from the skill's silence, not a directly confirmed absence — flagging accordingly rather than treating it as proven.)*
- **Community usage trackers exist and explicitly disclaim authority.** Third-party tools (SessionWatcher, ccusage-style CLIs, VS Code extensions) approximate usage by parsing the same local session transcripts this repo already reads, "not the source of truth for whether you can start another turn" [S3] — i.e., the community has already converged on transcript-parsing as the best available *local* proxy, precisely because no better signal exists, and even they caveat it as an estimate.
- **No OTel/telemetry-based usage-limit signal found.** No source (skill or web) documented an OTel export carrying subscription-quota data; `CLAUDE_CODE_ENABLE_TELEMETRY` (referenced elsewhere in this project's own wiki as an unexplored idea) covers cost/token telemetry export in general, not a "quota remaining" or "limit approaching" signal specifically — this remains unconfirmed either way and would need separate, dedicated verification if pursued.

## Constraints

- Any replacement signal must be a genuinely different mechanism from `claude usage` (nonexistent) or a full agentic turn (expensive, slow, unreliable — the original bug).
- The signal, if built at all, would have to be a **local heuristic** derived from transcript parsing (extending the existing `host-server/usage.ts` machinery) rather than an authoritative API/CLI query — because no authoritative query surface exists.
- A heuristic is inherently approximate: Anthropic doesn't publish the token-to-quota formula, can change quota mechanics without notice, and the official `/usage` view is itself described as a local-only estimate — so a heuristic built by this project would carry the same "not authoritative" caveat, one layer further removed.
- Per the requesting task's constraint: any change to `USAGE_CHECK_CMD`'s behavior is a change to a cost-control/safety mechanism and needs explicit sign-off before shipping — this applies doubly to a heuristic proxy, since a wrong heuristic could be worse than no signal (false confidence).

## Recommendation

**Ship nothing new right now. File the honest finding and treat `USAGE_CHECK_CMD='true'` (already deployed) as correct, not provisional.** The team already independently reached the safe state (no automated checking) before this research completed — that was the right call, not a placeholder awaiting a "real" fix, because no real fix is currently possible via any documented, scriptable surface.

**If/when the team wants an approximate signal anyway**, the only viable path is extending `host-server/usage.ts`'s existing transcript-parsing to also estimate proximity to a configured plan tier's rough session/weekly budget (user-supplied plan tier + published rough limits, refreshed as Anthropic's docs change), clearly labeled as an estimate in any UI/log output, never used to silently gate dispatch without a human-visible indicator. This is materially riskier than the previous recommendation's items 2–4 (call-once-per-tick, TTL cache, hard timeout, fail-open) suggested in the prior investigation, all of which remain valid *regardless* of what signal (if any) ends up behind them.

**Revisit if:** `anthropics/claude-code#33820` (or an equivalent feature request) ships, exposing rate-limit/quota data to hooks or scripts — that would be the first genuinely authoritative, scriptable signal for this use case and should replace any heuristic immediately.
