# Research: Stop hook payload, sub-agent-in-flight detection, and a sentinel-file design for BUG-0001

> The `Stop` hook's own JSON payload has **no field that reveals outstanding background-agent work** — and per Anthropic's docs, `Stop` is documented to fire only after all *synchronous* sub-agent work (the classic Task tool, `SubagentStart`/`SubagentStop`-bracketed) has resolved. BUG-0001's incident is consistent with a *different, newer* mechanism: Claude Code's **background/async agents** (shipped v2.1.198, several months after this repo last touched its hook set), which legitimately end the outer turn (a real `Stop`) while the background agent keeps running, resumed later via a `Notification` event. This repo used to have a `Notification` hook and removed it in April 2026 — **before** background-agent notification support existed — so the removal wasn't a rejection of this use case, just earlier than it existed. The two new `notification_type` values (`agent_needs_input`, `agent_completed`) are the concrete, event-driven signal needed to build a sentinel that works for arbitrarily long sub-agent waits, with no polling-cycle guesswork.

## Research Questions
- What exact JSON context does the `Stop` hook receive, and does it ever indicate a sub-agent is still running?
- Does `Stop` fire while a Task-tool (or background-agent) sub-agent is still in flight?
- Is there any Claude Code signal that reveals "this agent has outstanding background/async sub-agent work"?
- How could a sentinel-file mechanism be designed so it works for arbitrarily long sub-agent waits (not a fixed N-cycle grace period), across whichever idle-detection path (hook state file, `monitor.sh`'s regex fallback, host-server's read-only re-evaluation) ends up gating dispatch?
- What does this repo's own history say about a prior `Notification` hook, and is resurrecting/extending it sound given why it was removed?

## Current State (Codebase)

- `hooks/on-stop.js` → `hooks/lib/write-state.js::writeState('idle', 'stop')` (`hooks/on-stop.js:2`). `writeState()` reads the hook JSON payload from stdin but only ever extracts `transcript_path`, `session_id`, and `model` (`hooks/lib/write-state.js:92-109`) — it never inspects `agent_id`/`agent_type`/anything sub-agent-related, and writes `idle` unconditionally whenever it's invoked. [S7]
- `install-hooks.sh` / `hooks/register-hooks.jq` register `on-stop.js` under the `Stop` event only (`register("Stop"; ...)`, `hooks/register-hooks.jq:68`) — no `SubagentStop`, no `Notification`. [S8]
- **This repo used to have a `Notification` hook.** `hooks/on-notification.sh` (introduced commit `1f55cfe`, Apr 16 2026) routed `notification_type` to state: `idle_prompt→done`, `permission_prompt|elicitation_dialog→wait`, `auth_success→nop`, unknown→log-only. It was **deleted** one day later in commit `a17ef24` ("Complete tasks 009+010: collapse hook state to idle/busy") as part of a deliberate simplification from a 4-value state vocabulary (`done`/`working`/`wait`/`dispatching`) down to 2 (`idle`/`busy`). The task doc for that change (`.docs/tasks/completed/009-hook-model-alignment.md`, read via `git show`) gives the reason as vocabulary simplification — it says nothing about background agents, sub-agent tracking, or rejecting Notification as a signal source. [S9]
- `scripts/monitor.sh::is_idle()` (line 134) and `dispatch()` (line 321, dispatch call site 438-439) are the exact integration point where a sentinel-gate would need to plug in: `mark_busy()` (line 313) already writes an intermediate `busy` state right before `send-keys`, so a "hold dispatch" check belongs in the same neighborhood — right before `pop_task_sql` is called at the dispatch call site. TASK-120/TASK-121 (both `todo`) plan to move this trigger into `host-server`'s 2s status-poll loop (`pollAndDiff`) instead of `monitor.sh`'s loop — any sentinel-gate design should work from either call site, since both ultimately just read the same on-disk state.
- `CLAUDE.md`'s own architecture section documents `awaiting`/`stalled` as **derived, non-hook-written** statuses computed from pane-text pattern matching with staleness fallbacks (`AWAITING_PATTERN`, `busy`-older-than-2×POLL_INTERVAL→`stalled`) — i.e. this codebase already has a working precedent for "a status beyond raw idle/busy, with a bounded staleness fallback so it can't get stuck forever." A sentinel-gate for background-agent-pending should follow the same shape.

## Key Findings

- **`Stop`'s JSON payload, verified against two independent primary sources**, contains: `session_id`, `prompt_id`, `transcript_path`, `cwd`, `permission_mode`, `effort.level`, `hook_event_name`, `last_assistant_message`, and (only when the hook fires *inside* a subagent context) `agent_id`/`agent_type`. [S1][S2] None of these fields describe "other agents this session has outstanding." `last_assistant_message` is the closest thing to a free-text signal, and it's unstructured — not a reliable mechanism.
- **`Stop` is documented to fire only after all sub-agent work has resolved**, for the classic synchronous Task-tool mechanism: "Stop fires only after all subagent work has completely resolved" — the lifecycle nests `SubagentStart`/`SubagentStop` *inside* the outer turn, and `Stop` is the outer turn's own completion. [S1] This means a **standard** Task-tool sub-agent cannot be "still running" at the moment `Stop` fires — which argues against a literal `SubagentStop`-misrouted-to-`Stop` explanation for BUG-0001, consistent with the reporter's own observation that this specific failure mode has never come from ordinary sub-agent use before.
- **Claude Code shipped background/async agents in v2.1.198 (~July 1, 2026)** — several months after this repo's hook set was last touched (April 2026). "As of v2.1.198, background agents run by default, and the Notification hook fires `agent_needs_input` and `agent_completed` events for background sessions." [S3] This is a *different* mechanism from the synchronous Task tool: the outer turn genuinely ends (a real, correct `Stop`) while a background agent keeps running independently, and Claude Code later resumes the conversation via its own async task-notification machinery — matching the reporter's description of the pane "coming to a full stop" (not spinning) while the transcript showed it explicitly waiting on a background sub-agent.
- **`notification_type` values, cross-verified via two independent fetches of the same canonical doc** (`code.claude.com/docs/en/hooks`), include: `permission_prompt`, `idle_prompt`, `auth_success`, `elicitation_dialog`, `elicitation_url_dialog`, `elicitation_complete`, `elicitation_response`, `agent_needs_input`, `agent_completed`. [S4][S5] The verbatim second fetch confirms this list is a literal matcher-table quote, not a summarization artifact. **This is the concrete, structured signal for "a background agent is outstanding vs. resolved."**
- What exactly `agent_needs_input` covers is **not fully pinned down by this research** — is it "background agent is running and just needs your attention for a decision" (i.e. only a subset of the running window) or a general "still active" ping? *(inference — no primary source spells out the precise semantics or payload fields of these two notification types; a live payload capture is needed before implementation.)* Likewise unconfirmed: whether the payload carries a correlator (e.g. `agent_id`) usable to track *which* background agent completed when multiple run concurrently — plausible by analogy with `SubagentStop`'s `agent_id` field, but not directly verified for `Notification`.
- **No hook event was found that fires at the moment a background agent is *dispatched*** (a "started" counterpart). The candidate for that half of the signal is a `PreToolUse` hook matched against whichever tool call initiates background/async agent work — but this repo's own `Agent`/`Task`-tool usage is not exclusively async (most sub-agent calls are synchronous, already covered by `Stop`'s documented wait-for-completion behavior), so naively incrementing a pending-count on every `PreToolUse` match would over-trigger for ordinary synchronous sub-agent use. *(inference — no primary source confirms how to syntactically distinguish a background/async agent dispatch from a synchronous one in `tool_input`; needs live payload inspection.)*

## Constraints

- Any fix must not resurrect the exact behavior TASK-009 deliberately removed (the full `done`/`working`/`wait`/`dispatching` 4-state vocabulary) — a narrow, purpose-built sentinel (separate from the `idle`/`busy` state file) is a better fit than reopening that vocabulary.
- The mechanism must tolerate **arbitrarily long** background-agent runtimes per the reporter's explicit constraint — ruling out a fixed-N-poll-cycles grace period as a complete fix (it can still be a *belt-and-suspenders* fallback, not the primary mechanism).
- Must degrade safely: if the `Notification` signal is ever missed (hook failure, Claude Code version drift, notification type Claude Code adds later), the sentinel must not permanently block dispatch — needs the same kind of staleness/TTL fallback the codebase already uses for `stalled` (busy-older-than-2×POLL_INTERVAL).
- Exact field names/behavior of `agent_needs_input`/`agent_completed` are not fully confirmed from documentation alone — implementation must start with a live, controlled capture (dump full payloads to a log file, as the existing hooks-reference memory's debugging checklist §8 already recommends) before wiring real logic.

## Recommendation

**Recommended approach: event-driven sentinel keyed to the `Notification` hook's `agent_completed`/`agent_needs_input` types, not a fixed grace period.**

Implementation outline:
1. **Investigate first, live**: re-add a minimal `hooks/on-notification.sh` (or `.js`, matching the current Node.js hook convention) that does nothing but log the full JSON payload to `$STATE_DIR/hook.log`, register it under `Notification` in `install-hooks.sh`/`register-hooks.jq`, then reproduce a real background-agent-spawning run (e.g. `/power-mode` or any skill known to dispatch async work) and capture real `agent_needs_input`/`agent_completed` payloads — confirming field names (especially any correlator like `agent_id`) before writing real logic. This directly resolves the two *(inference)*-flagged gaps above.
2. **Sentinel structure**: one file per outstanding background agent under a per-agent directory, e.g. `$STATE_DIR/<agent>.pending-agents/<correlator>`, written on the confirmed "agent still outstanding" signal and removed on `agent_completed`. Per-file (not a single counter) avoids read-modify-write races between concurrent Node hook processes — creation/deletion of a uniquely-named file is atomic; incrementing a shared counter is not.
3. **Dispatch gate**: in `scripts/monitor.sh`'s dispatch call site (around `mark_busy()` / `pop_task_sql`, `monitor.sh:438-439`) and the equivalent future `host-server` `pollAndDiff` path (TASK-120/121), require the sentinel directory to be empty (or absent) in addition to `is_idle()` before dispatching the next queued task.
4. **Staleness fallback**: mirror the existing `stalled` pattern — a sentinel file older than some bound (configurable, generous — e.g. tens of minutes, not `POLL_INTERVAL`-scale) is treated as stale and ignored, so a missed/failed `agent_completed` notification can't permanently wedge the queue. Log loudly when this fallback fires so it's visible, not silent.
5. Do **not** rely on a "started" signal from `PreToolUse` matching until the payload-shape investigation in step 1 confirms a reliable way to distinguish background/async dispatch from a synchronous sub-agent call — start with `agent_completed`-only cleanup of a sentinel that some other, confirmed mechanism populates, rather than guessing at the increment side first.

**Risks and mitigations:**
- *Risk*: `agent_needs_input`/`agent_completed` semantics turn out not to map cleanly to "background agent still running." *Mitigation*: step 1's live capture is a cheap, fast way to falsify this before investing in the dispatch-gate wiring.
- *Risk*: reintroducing a `Notification` hook regresses the TASK-009 simplification. *Mitigation*: scope it narrowly (only these two notification types feed the sentinel; everything else is a no-op/log-only, same as the original `on-notification.sh`'s `*` branch) rather than reviving the full `done`/`wait` vocabulary.
- *Risk*: Claude Code changes these notification types again (this feature is only ~6 weeks old as of this research). *Mitigation*: the staleness fallback (constraint above) means a broken signal degrades to "occasionally dispatches a bit early again," not "permanently stuck," while remaining loudly logged for someone to notice and update.

**Alternative if constraints change**: if a reliable "started" signal is found in step 1's investigation (e.g. a distinguishable `PreToolUse` shape for background dispatch), the sentinel can be self-contained (increment+decrement both hook-driven) instead of needing some other component to seed it — strictly better once confirmed.
