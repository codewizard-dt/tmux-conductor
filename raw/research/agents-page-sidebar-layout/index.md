# Research: Agents Page Sidebar Layout Refactor

> The current Agents page (`frontend/src/pages/AgentsPage.tsx` → `AgentList.tsx`, ~2100 lines) renders agents into three Kanban-style status columns and opens a full detail view (`AgentDetailModal`) as an overlay. The requested refactor replaces the Kanban board with a single project-grouped sidebar list (status shown as a right-border color) and moves the modal's content into the main content area, matching the "list + detail pane" pattern React Router's own docs recommend for exactly this shape (sidebar nav + `Outlet` detail pane). The app already depends on `react-router-dom` v7 and already has multiple top-level routes, so the detail pane can be addressed by URL (`/agents/:agentId`) instead of local `useState`, which also fixes the existing "can't deep-link or refresh into an open agent" limitation.

## Research Questions
1. What does the current Agents page/AgentList component structure look like, and which parts are Kanban-specific vs. reusable?
2. Where does project grouping already exist, and can it be reused for the new sidebar?
3. What is `AgentDetailModal`'s prop surface, and what does it depend on that a non-modal, route-driven detail pane would need to reproduce (keyboard nav, escape-to-close, notifications, etc.)?
4. Does the existing status model provide a color already suitable for a border indicator?
5. What's the standard, low-risk way to convert a modal-driven detail view into a routed sidebar+detail layout in a React Router v7 app that isn't using the newer data-router/loader APIs?

## Current State (Codebase)

- **Entry point**: `AgentsPage` (`frontend/src/pages/AgentsPage.tsx:7-31`) is a thin wrapper — "+ Add Agent" button, `InactiveAgentsPanel`, `AddAgentForm`/`AddBgProcessForm` modals, and `<AgentList />`. All the real layout logic lives inside `AgentList.tsx`.
- **Kanban structure**: `AgentList.tsx` defines `COLUMNS` (`attention` / `busy` / `ready`, `AgentList.tsx:1280-1284`) and `columnFor()` (`:1290-1295`) which buckets each agent's `AgentStatus` into one of three columns; statuses not in any column (`no-window`, `exited`, `unknown`) render in a separate "inactive" section. The main `AgentList` component (function starting ~`:1700`) partitions `agents` into `columnAgents` per column (`:2019`), sorts each with `byProjectThenStatus` (`:2005`), and renders three column sections side by side — this is the code that must be deleted/replaced wholesale.
- **Project grouping already exists** as a *sort comparator*, not a grouped render: `projectLabelFor`/`projectIdFor` (`:2000-2001`) read `agent.projectName`/`agent.projectId` directly off the `Agent` object, and `byProjectThenStatus` (`:2005`) sorts by project label first, then by `STATUS_SORT` order (`:1256-1270`), so agents already carry everything needed to group-by-project — there is no separate "project grouping" component to build from scratch, just a fold/group step in place of the current three-way column partition. `BgProcessSection` has an analogous, already-grouped pattern (`groupBgsByProject`, `bgProjectIdFor`/`bgProjectLabelFor`, `:1562-1610`) worth mirroring for consistency.
- **Status → color mapping already exists** and is exactly what a right-border indicator needs: `STATUS_CONFIG` (`AgentList.tsx:89-101`) maps every `AgentStatus` to `{ bg, color, dot, label }`; `getStatusColor()` (`:103-105`) already returns `STATUS_CONFIG[status].dot`, a single hex value per status, ready to hand to a `border-right-color` style. No new color system is needed — only a new place to consume `getStatusColor()`.
- **The modal**: `AgentDetailModal` (`AgentList.tsx:588` onward, this is the single largest function in the file) takes `{ agent, project, projectId, status, onClose, armInteract, agentCount, onNavigate, onRenamed, onCloned, onRoleChanged }`. Internally it owns ~20 pieces of `useState` (queue tasks, worktree creation, rename/role/clone flows, interact-mode toggling, per-tab presence flags for `AgentInfoTabs`) and several `useEffect`s: one that locks `document.body.style.overflow` for the modal-open state (`:647-651`, becomes unnecessary once it's not an overlay), one that force-activates the "terminal" tab when opened via a notification CTA (`:657-660`), one that fetches queued tasks + skills per-agent (`:662-673`), and one that binds a global `Escape` keydown listener to `onClose` unless `interacting` is true (`:675-680`, must be reconsidered once "close" means "navigate away" rather than "dismiss overlay"). None of this internal logic is Kanban- or modal-specific — it's agent detail logic that can move into a page/route component largely as-is.
- **Modal open/close & keyboard nav state** lives in the parent `AgentList`, not the modal: `expandedAgent` (`{ id, armInteract } | null`, `:1714`) is the single source of truth for which agent's detail is open; `handleNavigate` (`:1730`) implements Cmd+Shift+Arrow cycling between *active* agents only (skips inactive ones); SSE notification handlers read `expandedAgentRef`/`agentsRef` mirrors to avoid stale closures (`:1754-1763`); clicking a notification toast also opens the modal via `setExpandedAgent({ id, armInteract: true })` (`:2103-2105`). This open/navigate state is the part that most directly needs to become a router concern (`useParams`/`useNavigate`) instead of local `useState` if the new layout is to be addressable by URL — but it can equally stay as local state if the team prefers not to introduce routing here (see Recommendation).
- **Routing**: `frontend/src/App.tsx` already uses `react-router-dom` v7.17 (`react-router-dom": "^7.17.0"` in `frontend/package.json`) with a conventional (non-data-router) `<Routes>`/`<Route>` tree: `/`, `/projects`, `/projects/:id`, `/history`. There is no existing `/agents/:id` route — introducing one is additive, not a breaking change to existing routes, and the app is already comfortable with `:id`-style params (`/projects/:id`).
- **Tests**: `AgentList.test.tsx` has explicit comments anchoring current behavior to the Kanban structure — e.g. "// from AgentList's own kanban columns — they render in InactiveAgentsPanel.tsx instead" (`:426`) and "// kanban's byProjectThenStatus/groupByProject grouping" (`:691`) — confirming the column/grouping behavior is under test today and that test suite will need rewriting alongside the component, not just patching.

## Key Findings

- The three ingredients the refactor needs — per-agent project label/id, per-status color, and a fully-formed detail view independent of its container — **already exist** in the codebase; the work is almost entirely about *removing* the column-partition rendering and *re-plumbing* how "which agent is open" is represented and displayed, not building new data plumbing. [S1]
- `AgentDetailModal` is large (the biggest function in `AgentList.tsx`) and self-contained enough (all its own `useState`/`useEffect`, fetches via `agent.id` only) that it can be relocated into a dedicated detail component/page with modest changes: primarily removing the `overflow:hidden` body-lock effect and reconsidering the `Escape`-closes behavior for a non-overlay context. [S1]
- React Router's own tutorial documentation describes this exact target shape — "sidebar list + detail pane driven by `Outlet`" — as a first-class supported pattern (`layout("layouts/sidebar.tsx", [index(...), route(":id", ...)])`, with an index route to avoid a blank detail pane when nothing is selected). This app doesn't use the newer `RouteConfig`/loader style shown in that doc, but the same shape (`<Route element={<SidebarLayout/>}><Route index .../><Route path=":agentId" .../></Route>`) is directly expressible with the `<Routes>/<Route>` API already in use in `App.tsx`. [S2]
- Keyboard cycling (Cmd+Shift+Arrow) and cross-tab "open via notification" behavior are currently implemented against local component state (`expandedAgent`) with ref-mirrors to dodge stale closures in SSE handlers — this is the trickiest part to carry over correctly regardless of whether the new "selected agent" lives in a route param or in local state, since notifications need to update "current selection" from an SSE callback either way. [S1]

## Constraints

- Must not regress: keyboard-driven agent cycling (Cmd+Shift+Arrow, skips inactive agents), notification-toast → open-agent-and-arm-interact flow, and per-tab (`AgentInfoTabs`) present/absent logic for Diff/Usage tabs.
- `AgentList.test.tsx` encodes current Kanban/grouping assumptions directly in test comments and will need a substantial rewrite in lockstep with the component change, not just incremental patching.
- The existing status color source (`STATUS_CONFIG`/`getStatusColor`) should be reused verbatim for the right-border indicator — introducing a second status-color mapping would create drift risk.
- `InactiveAgentsPanel` (no-window/exited/unknown agents) currently renders outside the three Kanban columns already, so it is largely unaffected by the column removal — only the "should the sidebar also list inactive agents, and how" question is new scope.
- Bg-process grouping (`BgProcessSection`) already parallels the project-grouping pattern that the sidebar will need for agents — worth designing the shared grouping utility once, for both.

## Recommendation

This is confirmed as roadmap-shaped work (multi-phase UI restructure, not a single task): tear out the Kanban partition, introduce project-grouped sidebar rendering keyed off already-available `projectLabelFor`/`projectIdFor`, add a status-colored right border using the existing `STATUS_CONFIG`/`getStatusColor`, and relocate `AgentDetailModal`'s content into a main-content-area detail view — optionally, but not necessarily, backed by a new `/agents/:agentId` route so the currently-modal-only view becomes deep-linkable and refresh-safe. Sequencing and the routed-vs-local-state decision are exactly what the roadmap's phases and the Q&A in this skill should pin down next; no further research is needed to start phasing this.

## Scope Addendum (user-supplied mid-research)

The user expanded scope beyond the original Kanban/sidebar/modal ask to include three more relocations, all of which turn out to be small deltas on existing components rather than new build:

- **`NavBar.tsx`** (`frontend/src/components/NavBar.tsx:9-54`) already exists as the app's top bar — a sticky header with nav links (Agents/Projects/History) and a theme toggle, `ml-auto`-pinned on the right. "Move Add Agent / Add Background Process up to the top bar" means adding two trigger buttons here, before or alongside the theme toggle. [S7]
- **`AddAgentForm`** (used today at `AgentsPage.tsx:20` as `<AddAgentForm open={showAddAgentModal} onClose={...} />`) is *already* modal-shaped (takes `open`/`onClose`) — only its trigger button needs to move from `AgentsPage` into `NavBar`.
- **`AddBgProcessForm`** (`frontend/src/components/AddBgProcessForm.tsx:24-234`) is currently an always-rendered inline card with no `open`/`onClose` props at all (mounted unconditionally at `AgentsPage.tsx:22`) — turning it into a modal is a real (small) code change: add `open`/`onClose` props mirroring `AddAgentForm`'s pattern, wrap its existing form markup in the same modal chrome, and move its trigger button to `NavBar`. [S8]
- **`InactiveAgentsPanel`** (`frontend/src/components/InactiveAgentsPanel.tsx:12-167`) already implements exactly the target interaction — a `collapsed`/`setCollapsed` toggle (default collapsed), a `▸`/`▾` disclosure row, and a list of inactive agents each opening `AgentDetailModal` on click, with its own prev/next `navigateExpanded`. This entire component's *behavior* is reusable as-is; the work is relocating it from `AgentsPage`'s standalone card (currently rendered beside the "+ Add Agent" button at `AgentsPage.tsx:12-17`) into a collapsible section docked at the top of the new sidebar, and re-pointing its "open detail" action at whatever mechanism the main Kanban-removal work adopts (routed page vs. local state) instead of its private `AgentDetailModal` instance. [S9]

None of these three additions require new state-management patterns — they reuse `open`/`onClose` (already established by `AddAgentForm`), the `collapsed` disclosure pattern (already established by `InactiveAgentsPanel`), and `NavBar`'s existing `ml-auto` right-aligned button slot.
