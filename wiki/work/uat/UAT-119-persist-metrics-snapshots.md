# UAT-119 — UAT: Persist periodic liveUpdateMetrics snapshots to observability.jsonl so metrics survive a host-server restart

> **Independent-eye note**: TASK-119 was implemented by a different agent (uatgen-068); this UAT was generated by a separate agent with no access to that implementation session, verifying purely from the landed source and the live running host-server.

> **Timing correction to the task's own framing (found during research, not assumed)**: the task's Step 3 notes "an edited `METRICS_SNAPSHOT_INTERVAL_MS` takes effect within 5s without a restart" — this is only exactly true of `readConductorConf()`'s own cache staleness window (`config.ts:50`, `CACHE_TTL_MS=5000`). Reading `startManagedLoop` itself (`host-server/index.ts:2410-2451`) shows the delay-getter (`() => readConductorConf().metricsSnapshotIntervalMs`) is only re-resolved when the *next* `schedule()` call happens, i.e. when the **currently pending** timer fires — not on a fixed 5s cadence of its own. If a conductor.conf edit lands partway through an already-running 60s interval, the new value cannot take effect until that in-flight 60s timer completes; only a subsequent test lowering the interval and waiting for that first re-schedule would see it apply, up to just under 60s later in the worst case. UAT-CLI-003 below sizes its wait window (~70s) around this corrected understanding rather than the task's "~5s" framing, so it doesn't produce a false failure on unlucky timing.

### UAT-CLI-002: liveUpdateMetrics.startedAt is invariant within a contiguous process run, and restarts never interleave in the log
- **Scenario**: `liveUpdateMetrics.startedAt` is set exactly once, at module load (`index.ts:333`, `startedAt: new Date().toISOString()`), and never reassigned afterward — every `metrics_snapshot` line written by the same host-server process must therefore embed the identical `startedAt` value for as long as that process runs. This is the property TASK-117/TASK-118 (unlanded ROADMAP-017 Phase 2 siblings) depend on to detect a restart when diffing consecutive snapshot lines: a *changed* `startedAt` between two lines is the restart signal a consumer must reset its delta baseline on; an *unchanged* `startedAt` means the cumulative counters in `liveUpdateMetrics.timings`/`.tmuxOperations`/etc. can be safely diffed against each other.
  > **Scoping note (do not revert to a whole-file `unique|length==1` check):** an earlier version of this case asserted `startedAt` was unique across the *entire* `observability.jsonl` file. That only holds until the very first host-server restart, after which the file legitimately accumulates multiple `startedAt` values forever — the assertion degrades into a permanent false failure the moment any restart occurs (caught live during a `/uat-auto` run on 2026-08-15: 3 distinct values had accumulated across 64+ lines after two real restarts, well before this file was ever walked to completion). The durable property worth pinning is scoped **per contiguous run**, not per file: (a) the *trailing* block of lines sharing the current process's `startedAt` is non-empty and internally consistent, and (b) distinct `startedAt` values never interleave — each one forms exactly one contiguous run in file order (this is the thing that would actually indicate a real bug: lines from two different process lifetimes being written out of order).
- **Steps**:
  1. Ensure `logs/observability.jsonl` has at least 1 `metrics_snapshot` line (per Prerequisites).
  2. Run the command below as-is.
- **Command**:
  ```bash
  jq -s '[.[] | select(.event=="metrics_snapshot") | .liveUpdateMetrics.startedAt] as $vals | ($vals[-1]) as $last | ($vals | reverse) as $rev | (reduce $rev[] as $v ({stop:false, count:0}; if .stop or $v != $last then .stop=true else .count += 1 end) | .count) as $trailing_run | (reduce $vals[] as $v ({prev: null, groups: []}; if .prev == $v then . else .groups += [$v] | .prev = $v end) | .groups) as $collapsed | ($vals | length) > 0 and $trailing_run > 0 and (($collapsed | length) == ($collapsed | unique | length))' logs/observability.jsonl
  ```
- **Expected Result**: Prints `true`. Three conditions must all hold: at least one `metrics_snapshot` line exists; the trailing contiguous run of lines sharing the *last* line's `startedAt` is non-empty (the current process has written at least one consistent snapshot); and collapsing consecutive equal `startedAt` values into runs yields no duplicate run-labels (proving no two lines from different process lifetimes are interleaved — each restart's block is contiguous). Verified live at generation/repair time: `n=80`, `last="2026-08-15T18:26:24.997Z"`, `trailing_run=44`, `no_interleaving=true` → `true`. Also sanity-checked the interleaving detector against a synthetic bad case (`["A","A","B","A"]` → correctly flags `no_interleaving: false`), confirming this is a real check, not a vacuous one.
- **Repeatable Unit Test**: Not applicable: same reasoning as UAT-CLI-001 — this property only exists across multiple real writes from a live, continuously-running process (and across a real restart boundary, for the interleaving half); there is nothing to unit-test in isolation.
- [x] Pass <!-- 2026-08-15 -->
