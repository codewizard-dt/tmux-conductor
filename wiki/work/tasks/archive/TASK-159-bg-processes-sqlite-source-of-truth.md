# TASK-159 — Make SQLite the sole source of truth for bg-process definitions and links

## Objective

Implement `ROADMAP-020` Phase 1: fix the live split-brain where `host-server/index.ts`'s bg-process routes read/write `conductor.conf` (via `host-server/config.ts`'s `appendBgProcessToConf`/`removeBgProcessFromConf`/`addBgLink`/`removeBgLink`) while `scripts/lib/db.sh` — used by `conductor.sh`/`spawn.sh`/`monitor.sh`/`teardown.sh` to actually spawn, link-env-inject, and liveness-check bg processes — reads SQLite exclusively. Rewire the routes onto `host-server/db.ts`'s existing (already-implemented, currently-uncalled) `createBgProcess`/`deleteBgProcess`/`listBgProcesses`, so dashboard-created bg processes — and their agent links — actually take effect the next time `conductor.sh`/`spawn.sh` runs.

Full research and citations: `raw/research/shared-dev-commands/index-2.md` and `sources-2.md`, plus the original `raw/research/shared-dev-commands/index.md`. Wiki: `wiki/knowledge/concepts/background-process-registry.md`, `wiki/knowledge/entities/components/host-server.md`.

## Approach

This is a pure rewire, not a schema change — `bg_processes` (including its `linked_agent_id` column) already exists in SQLite and is already what the bash scripts read (`scripts/lib/db.sh`'s `load_bg()` for definitions, `load_agents()`'s SQL join on `linked_agent_id` for the link-driven `CONDUCTOR_BG_NAME`/`LOG`/`STATE` env injection in `conductor.sh`/`spawn.sh`). Nothing on the bash/tmux/env-injection side changes. The fix is confined to `host-server/index.ts` (four route handlers + `buildBgStatuses`) and `host-server/config.ts` (removing the now-dead writer functions).

Key design decisions:
- **`linkedAgent` arrives as an agent name, `linkedAgentId` is a numeric FK.** Resolve via `listAgents(db).find(a => a.name === linkedAgent)`. Agent names are only unique *per project* (`idx_agents_project_name`/`idx_agents_null_name`) and `bg_processes` has no `project_id` yet (that's `TASK-156`, independent of this task) — so a bare-name lookup can in principle be ambiguous across projects. Accept the first match and 400 on no match; do not attempt project-aware disambiguation here — that's explicitly out of scope until `TASK-156` lands.
- **Do not touch `conductor.conf`'s `BG_PROCESSES=()`/`AGENT_BG_LINKS=()` blocks, or `readConductorConf`'s parsing of them into `ConductorConf.bgProcesses`/`agentBgLinks`.** `host-server/db.ts`'s `seedFromLegacy()` still reads `conf.bgProcesses`/`conf.agentBgLinks` once, on first-ever DB open, to import any pre-existing conf-defined bg processes into SQLite — that one-time path must keep working.
- **Only remove `config.ts`'s four writer functions** (`appendBgProcessToConf`, `removeBgProcessFromConf`, `addBgLink`, `removeBgLink`) — each has exactly one caller file (`index.ts`) and exactly the call sites listed in Step 1/2 below (confirmed via project-wide search during research); removing them once those call sites are gone leaves no dangling references. `clearConfCache`, `readConductorConf`, `DEFAULT_CONF_PATH` stay imported in `index.ts` (other live uses elsewhere in the file).
- **No frontend changes.** `AddBgProcessForm.tsx` and `AgentList.tsx`'s `BgProcessSection`/`BgProcessRow` only depend on the `POST/DELETE /bg-processes[/window]` JSON request/response shapes, which this task does not change — only the storage underneath moves.
- **No test harness exists today for Fastify routes in this repo** (confirmed: no `fastify.inject`/route-level test file for any endpoint, bg-process or otherwise) — the established pattern is DB-level unit tests (`db.test.ts`) plus manual/live verification. Follow that convention rather than introducing a new route-test harness as a side effect of this task.
