# TASK-0184 — Detect outstanding background jobs in agent status detection via ~/.claude/jobs/*/state.json

relates_to::[[BUG-0001]]
relates_to::[[TASK-133]]

> Implements `[[BUG-0001]]` option 2 (see its 2026-09-19 update). Does not touch `host-server/pendingAgents.ts` / `hasPendingBackgroundAgents()` — that hook-driven sentinel stays exactly as-is and keeps gating dispatch; this task adds a second, independent signal that gates **status detection** instead, which nothing currently gates (see Objective).

## Objective

Fresh repro 2026-09-19 (`tmp/dashboard-drops/1789799698836-Screenshot-2026-09-19-at-1.02.12-AM.png`): an agent's pane transcript shows an in-progress teammate/sub-agent conversation while the dashboard badges it `NO TASKS` (frontend's `empty` status: `idle` state + zero queued tasks). Root cause confirmed: `host-server/state.ts`'s `detectAgentStatus()` never calls `hasPendingBackgroundAgents()` — that check only gates the two dispatch call sites in `index.ts` (`host-server/index.ts:949`, `:2637`), so even on ticks where dispatch is correctly held, the **displayed** status is still wrong. `BUG-0001`'s own investigation additionally found the hook-driven sentinel itself has a load-bearing gap (a background agent that never calls `agent_needs_input` gets no sentinel at all), so fixing `detectAgentStatus()` to consult `hasPendingBackgroundAgents()` would still miss the common case.

This task adds a second, independent signal — polling Claude Code's own per-background-job state at `~/.claude/jobs/<id>/state.json` — that does not depend on the Notification hook firing at all, and wires it into `detectAgentStatus()` so an agent with a genuinely outstanding background job reports `busy`, not `idle`.

## Approach

**The correlator (new finding, not in BUG-0001 before today).** `~/.claude/jobs/<id>/state.json` has no field naming which session spawned it. But the *spawning* session's own transcript `.jsonl` gets a dedicated record when it dispatches a background job:

```json
{"type":"continued-in","sessionId":"<parent-session-id>","continuedInSessionId":"<job-session-id>"}
```

Verified live against two unrelated real jobs on this machine (`~/.claude/jobs/5aa8a27d/`, `~/.claude/jobs/7290ca9d/`) — each job's `sessionId` (from its own `state.json`) was found as a `continuedInSessionId` in exactly one other transcript, and that transcript's own top-level `sessionId` was the actual parent session. This repo already resolves an agent's own transcript path via `resolveTranscriptPath()` in `host-server/context.ts` (reads the hook-written sidecar `${stateDir}/${agentName}.meta.json` → `{transcript_path, session_id}`, falling back to newest-file-in-project-dir derivation when the sidecar is missing) — reuse it rather than re-deriving transcript resolution.

**Do not assume the jobs-directory name is `sessionId.slice(0, 8)`.** Two observed job dirs (`5aa8a27d`, `7290ca9d`) happen to match their session id's first 8 hex chars, but that truncation rule is not documented or confirmed stable. Enumerate `~/.claude/jobs/*/state.json`, parse each, and match by the job's own `sessionId` field against the set of `continuedInSessionId`s collected from the agent's transcript — never construct a job-dir path from a truncated session id.

**Unconfirmed: the full `state` enum.** Observed so far: `"working"` (non-terminal, seen in a job's `timeline.jsonl`) and `"done"` (terminal, seen in `state.json`). Whether `"blocked"`/`"stopped"`/`"failed"`/others exist is unconfirmed — this task is investigate-then-implement (mirrors `TASK-133`'s shape): Step 1 captures real data before Step 2 hard-codes a terminal-state list. Whatever the enum turns out to be, the **staleness bound stays load-bearing regardless** — an unrecognized `state` value must log a loud warning and be treated as non-terminal (busy) only until the job's `updatedAt` ages past the staleness bound (reuse `conf.pendingAgentStaleMs` / `PENDING_AGENT_STALE_S` unless Step 1's real data shows background jobs need a materially different timescale), exactly mirroring `pendingAgents.ts`'s existing stale-sentinel fallback — so a format change can never wedge an agent's status at `busy` forever.

**Wiring: a wrapper, not a change to `detectAgentStatus()`'s tested matrix.** `detectAgentStatus()` has an 18-case unit-tested behavior matrix (`host-server/state.test.ts`) and 7 call sites in `index.ts`, none of which currently pass `workdir`. Rather than thread a new parameter through all 7 call sites and risk the existing matrix, add a new exported wrapper in `state.ts` (or a new small module — your call once you see the shape) that calls `detectAgentStatus()` unchanged, and only when its result is `{state: 'idle', ...}` additionally checks the new background-job signal and upgrades to `{state: 'busy', reason: 'background-job'}` (new `DetectionReason` member) if one is found. All 7 call sites in `index.ts` switch to the wrapper; `detectAgentStatus()` itself and its 18-case test file are untouched. The wrapper needs `agent.workdir` (already present on every `Agent`/call-site object — confirm with `find_referencing_symbols` on each site) and `conf.stateDir`.

**Performance.** This runs on every status poll (`buildSnapshot`'s per-agent loop, 2s cadence per `CLAUDE.md`). Reading and re-parsing an agent's full transcript every tick is wasteful for long sessions. Follow `context.ts`'s `readTranscriptInfo` pattern: cache by `(transcriptPath, mtimeMs, size)` so an unchanged transcript is never rescanned, and use the same cheap substring pre-check (`line.indexOf('"type":"continued-in"') === -1 → continue`) before `JSON.parse`-ing a line. `~/.claude/jobs/*/state.json` itself is small and few in number (readdir + parse per tick is fine; no caching needed there beyond what staleness already provides).

**Out of scope.** Do not touch `hooks/on-notification.js` or `host-server/pendingAgents.ts` — the dispatch-gating sentinel is unrelated and stays as-is. Do not attempt to fix the deeper "no reliable started signal" gap for dispatch gating (`BUG-0001`'s own scope) — this task is status-detection only.
