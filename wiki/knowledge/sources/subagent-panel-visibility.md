Two screenshots of the same Claude Code interactive footer looked different — one showed only the collapsed `← for agents` hint, the other showed three rows (`main`, `survey-req-dec`, `survey-roadmap-task`) listed underneath the prompt input. The apparent hypothesis was "background vs. agent teams," but that's not the mechanism.

**Two independent UI surfaces exist.** The `←` footer hint is a coarse, session/machine-wide signal (`← for agents` / `← N agents` / `← N done`) that opens the separate full-screen `claude agents` view; it was present in both screenshots. The **subagent panel below the prompt input** is a distinct, inline live tree that lists only the *current session's own* currently-running background subagents — this is the element that differed.

**Fork mode (default on since v2.1.225–233) is why subagents run in the background at all**, and background execution (default since v2.1.195–201, ~July 2026) is what makes a subagent eligible for a panel row: "Claude Code runs the subagent in the background, forks and non-fork subagents alike, and Claude can't ask for the foreground." Foreground subagents block the parent turn and never get a row. A row appears only while its subagent is actually running, and clears within 0–30 seconds of completion (immediately on success, up to 30s on failure/stop) — so the "hidden" screenshot is fully explained by simple timing (no subagent of *that session* in flight at that instant), with no need for a background-vs-team distinction.

Practical implication for `derived_from::[[Claude Code CLI]]`-based orchestration (this project's skills that dispatch `Agent(...)` calls, e.g. `/roadmap-assess`, `/bug-assess`, `/now`): to make dispatched agents reliably show as rows, dispatch them concurrently (multiple calls in one message) with explicit `name`s, and don't disable fork mode. The panel is a live-only view, not a durable log — for a persistent record, use `claude agents --json` instead (see `relates_to::[[Discovering All Active Claude Code Sessions on a Machine]]`).

See `relates_to::[[Background/async agent panel visibility (fork mode, foreground vs. background subagents)]]` for the generalized concept and `relates_to::[[Pane-Idle Detection Cannot See Async Background Agent Work]]` for the related (but distinct) idle-detection problem this project already solved for.

## Update (2026-09-13): agent teams is the likely real mechanism, not a ruled-out alternative

> **Contradiction — corrected:** the original pass above concluded panel visibility is "purely foreground-vs-background... not 'background vs. agent teams'" and treated agent teams as a separate concept "not what's pictured." A follow-up pass found this understated: this user's `~/.claude/settings.json` has `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS: "1"` set globally, and Claude Code launches a teammate — not a plain background subagent — whenever an `Agent(...)` call carries a `name` while agent teams is enabled (which Claude does routinely on its own, even when the calling prompt doesn't hardcode one). The two screenshots' named rows (`survey-req-dec`, `survey-roadmap-task`) were very likely genuine **teammates**, not plain subagents. See `derived_from::[[subagent-panel-visibility (update)|../../../raw/research/subagent-panel-visibility/index-2.md]]` for the full analysis.

Practically, this refines rather than reverses the original finding: foreground-vs-background is still what gates *whether* a row can appear at all, but **whether that row is a teammate or a plain subagent changes how long it stays visible** — a teammate's idle row persists in the panel while any sibling is still working (hiding only once the whole panel is idle, per the v2.1.199 behavior), while a plain subagent's row clears immediately on its own completion. `power-mode` (`derived_from::[[power-mode-skill]]`) explicitly says "Use agent teams for parallel work" in its own `SKILL.md`, dispatches multiple `Agent(...)` calls per message (satisfying the concurrency requirement), and very likely benefits from exactly this teammate-persistence behavior today — incidentally, via Claude's own auto-naming, rather than because its `SKILL.md` deliberately passes `name`. See `relates_to::[[claude-code-agent-teams]]`.

## Update (2026-09-13): where to put the "always name your parallel Agent calls" instruction

A third pass answered the follow-on question of *instruction placement* rather than mechanism: where to write down "prefer naming parallel `Agent(...)` calls" so it actually reaches every tmux-conductor-spawned agent. Two locations cover different scopes and both are worth using: `~/.claude/rules/agent-teams-preference.md` (new, user-level, loads unconditionally for every project on this machine — the same mechanism already backing `~/.claude/rules/lsp-first.md`) for true "every tmux agent regardless of workdir" coverage, plus a short cross-referencing note in this repo's own `CLAUDE.md` for anyone reading the project's own docs. `AGENTS.md` is the wrong place — Claude Code doesn't read it at all. See `derived_from::[[instruction placement for agent orchestration preferences|../../../raw/research/subagent-panel-visibility/index-3.md]]` and the new `relates_to::[[claude-code-instruction-placement]]` concept page for the full CLAUDE.md/rules/`--append-system-prompt` comparison.

## Update (2026-09-13): reaching agents in *other* projects specifically

A fourth pass traced exactly how tmux-conductor's own `launch_cmd` storage works, since the user specifically wanted the preference to reach agents spawned into **other** projects, not just this repo. Finding: `agents.launch_cmd` is a required string **frozen at agent-creation time** — never re-derived from its project afterward — and `projects.default_launch_cmd` is only a copy-on-create template (`POST /projects/:id/agents` resolves `launchCmdOverride ?? project.defaultLaunchCmd` once, at creation). Both real spawn paths (`scripts/conductor.sh`/`spawn.sh`'s `AGENT_CMDS`, and `host-server/index.ts`'s live single-agent spawn function for the dashboard's "Add Agent" flow) just interpolate whatever string is already stored, unmodified. **This means no source-code change is needed to propagate the preference** — only a data fix: update the three literal-default sites (SQL schema `DEFAULT`, `db.ts`'s `createProject` fallback, `AddProjectForm.tsx`'s `DEFAULT_LAUNCH_COMMAND`) so new projects/agents inherit `--append-system-prompt-file <rule-path>` going forward, plus a one-time backfill of every existing `agents`/`projects` row whose launch command is Claude Code's (gated by the same `detectAgentType()`/`launch_cmd_name()` logic the codebase already uses for idle/busy pattern selection, to avoid corrupting Codex/custom agents). See `derived_from::[[reaching other-project agents via launch_cmd storage|../../../raw/research/subagent-panel-visibility/index-4.md]]`.
