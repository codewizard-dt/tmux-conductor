# Background Process Registry (`bg_processes`) — Mechanism and Gaps

tmux-conductor's `bg_processes` concept is the existing mechanism for running a named, long-lived, non-agent command (a dev server, watcher, log tailer) as its own tmux window inside the shared conductor session. It is the natural extension point for "shared dev commands agents can check on," and understanding its current mechanism and gaps matters before building anything new on top of it.

**Mechanism** (three parts, all already implemented):
1. **Registry** — `name:workdir:launchCmd`, scoped to a project (`project_id`; the retired single-agent `linked_agent_id` link is no longer read or written, see below), identified by the derived slug `<projectName>-<name>` (see "Name uniqueness" below). Spawned as its own tmux window (named by the slug) by `scripts/conductor.sh`/`spawn.sh`; never dispatched to, never affects idle/usage-based shutdown (see `architecture/script-integration` in the project's Serena memory).
2. **Output capture** — `tmux pipe-pane -t $SESSION:=$slug -o "cat >> '$LOG_DIR/bg-$slug.log'"` (`$slug` = `<projectName>-<name>`; was the bare `$name` before [[TASK-0196]]), attached at spawn time. This avoids the buffered/color-stripped output that plain stdout redirection causes when a process detects it isn't attached to a real terminal — the same reasoning Procfile/tmux process managers like Overmind use for running each process in a real tmux window rather than piping file descriptors directly.
3. **Liveness** — `scripts/monitor.sh` writes `running`/`exited`/`dead` to `$STATE_DIR/bg-<slug>.state` on every poll tick, independent of the log file (originally `alive`/`dead` from a `tmux has-session` check alone; see the 2026-09-19 liveness update below).

Every agent (not just a linked one) already receives `CONDUCTOR_STATE_DIR` and `CONDUCTOR_LOG_DIR` as absolute-path environment variables at spawn, so in principle any agent can already resolve `bg-<slug>.log`/`bg-<slug>.state` paths for a *known* slug — see relates_to::[[Claude Code Hooks]] for how these env vars flow through the same spawn path as hook configuration.

**Known gaps, as of 2026-09-13** (see the full research at `raw/research/shared-dev-commands/index.md` for detail):
- **Split-brain source of truth**: `host-server/index.ts`'s `POST/DELETE /api/bg-processes` routes read/write `conductor.conf`'s `BG_PROCESSES` bash array, while `scripts/lib/db.sh`'s `load_bg()` (used by the shell scripts that actually spawn and monitor processes) reads the SQLite `bg_processes` table. The two are not synced. `host-server/db.ts`'s `createBgProcess`/`listBgProcesses`/`deleteBgProcess` are fully implemented but uncalled — dead code. This contradicts both CLAUDE.md's description ("Background processes are stored in the SQLite `bg_processes` table … not the `conductor.conf` `BG_PROCESSES` array") and the project's own `architecture/script-integration` Serena memory, both of which describe the pre-drift model.
- **No project scoping**: unlike `agents`/`tasks`/`schedules`, `bg_processes` carries no `project_id` — every bg process in a session is visible to every agent in that session with no per-project filter.
- **No agent-facing discovery command**: the `CONDUCTOR_BG_NAME`/`LOG`/`STATE` convenience env vars were only injected for one explicitly-linked agent (`AGENT_BG_LINKS`, one bg process → one agent; since retired by [[TASK-0197]]); nothing let any other agent ask "what's registered for my project" or cross-check a possibly-`POLL_INTERVAL`-stale state file against live `tmux has-session`.

**Design implication**: any future "list vital dev commands" / shared dev-process feature should extend this mechanism (fix the split-brain, add `project_id`, add a thin discovery script over the *existing* log/state file conventions) rather than build a parallel registry — a second registry would either duplicate the split-brain problem at a new layer or require reconciling two overlapping "named shared process" concepts in the UI and data model.

**UI project-grouping precedent (2026-09-13, see `raw/research/shared-dev-commands/index-3.md`)**: the dashboard already implements consecutive-run project grouping for agents — `frontend/src/components/AgentList.tsx:1561-1604`'s `projectLabelFor`/`projectIdFor`/`groupByProject` helpers, rendered as project sub-headers above each column's agent tiles (`AgentList.tsx:1637-1655`). `BgProcessSection`/`BgProcess` (same file, ~lines 55-63 and 1278-1288) has no equivalent grouping and no `projectId`/`projectName` fields yet on either the frontend `BgProcess` type or the backend `BgStatus`/`buildBgStatuses` (`host-server/index.ts:136-165`) — extending bg-process UI to group by project should reuse the existing `groupByProject` clustering shape rather than invent a new one, once those fields exist end-to-end (tracked as ROADMAP-020 Phase 2 → Phase 3, see [[TASK-156]]).

**Update (2026-09-13)**: the `project_id` gap now has a concrete implementation plan — see [[bg_processes Project Scoping — Migration and Endpoint Shape (ROADMAP-020 Phase 2)]] and `TASK-156`. Recommendation: a v1-shaped nullable `project_id` column (no per-project unique-index rebuild, since nothing requires bg-process names to be unique per project the way `agents` needed once `POST /projects/:id/agents` allowed duplicate names across projects) plus a new `GET /projects/:id/bg-processes` endpoint. The split-brain gap above was re-confirmed still live during that follow-up research.

> **Contradiction:** the "no per-project unique-index rebuild" recommendation above (and the global `UNIQUE` on `name`) was superseded on 2026-09-20: names are now unique per project via a `(project_id, name)` index and identity is a derived slug. See "Name uniqueness" below.

**Update (2026-09-13, ROADMAP-020 Phase 1 scoped)**: the split-brain fix itself (definitions **and** the bg↔agent link — see the refinement above) is now scoped as `TASK-159` (`wiki/work/tasks/TASK-159-bg-processes-sqlite-source-of-truth.md`; originally drafted as `TASK-157` but renamed after a same-session task-ID race — see `wiki/log.md`'s "TASK-159 created" entry), independent of and not blocked by `TASK-156`'s Phase 2 work. Per `raw/research/shared-dev-commands/index-2.md`, the fix touches exactly four call sites in `host-server/index.ts` (`POST/DELETE /bg-processes`, `POST/DELETE /bg-processes/:name/window`) plus `buildBgStatuses`, rewiring them onto `db.ts`'s `createBgProcess`/`deleteBgProcess`/`listBgProcesses`, and removes the now-dead `config.ts` writer functions (`appendBgProcessToConf`, `removeBgProcessFromConf`, `addBgLink`, `removeBgLink`).

**Update (2026-09-19, after ROADMAP-020 shipped)**: the split-brain, `project_id`, project-grouped UI, and `dev-commands` (`list`/`status`/`tail`) gaps above are closed. The remaining gaps are agent-facing: no restart primitive anywhere (open/close-window only; `POST …/window` 409s if the window exists), a project-blind skill and no project identifier in agent env, and `alive` meaning only "window exists" (a crashed process that drops to a shell prompt is not detected — inference). See [[Project-Linked Background Processes That Every Project Agent Can Inspect and Restart]].

### Real liveness (running / exited / stopped)

Outcome (2026-09-19): "alive" now means the pane is actually running the process, not just that its window exists. The API field `BgStatus.liveness` is `running` (pane runs a non-shell command), `exited` (window present but the pane fell back to a plain shell) or `stopped` (no window); `windowPresent` stays on the payload. The state file `$STATE_DIR/bg-<slug>.state` written by `scripts/monitor.sh` is `running`, `exited` or `dead` (`dead` = window not found, the old missing-window branch). Both use the same `#{pane_current_command}` rule as agent liveness (`isPaneDead` / `pane_dead()`), with two fail-toward-`running` exceptions: a launch command that is itself a shell, and an empty command string from tmux. Because a shell is briefly visible in the pane between `send-keys` and the child forking, the host-server's pure `bgLiveness()` applies `BG_STARTUP_GRACE_MS` (3 s), dated from the window's tmux `#{window_activity}`; the monitor's bash mirror (`bg_pane_exited()`) has no grace. Liveness is display-only: bg processes are still never dispatched to and never gate dispatch or teardown. The `skills/dev-commands/SKILL.md` wording fix is Phase 3 of ROADMAP-0024. `#{window_activity}` was confirmed on tmux 3.7c during UAT-0191 generation (2026-09-20, private socket): it expands to epoch seconds, which `readTmuxWindowInventory` converts to ms. The full live-session UAT run is still pending. derived_from::[[TASK-0191]]

### Unscoped bg processes

Policy (decided 2026-09-19, **tightened 2026-09-20**): every bg process must have a project — there is no project-less state. The 2026-09-19 decision (policy C) treated a `project_id IS NULL` row as a dashboard-only "Unassigned" orphan that agents could not see and could not restart; the 2026-09-20 amendment removes the orphan state instead of tolerating it. Implemented by [[TASK-0195]] (2026-09-20): `POST /bg-processes` requires an integer `projectId` and returns 400 for a missing, non-integer or unknown one (validated before the tmux session check); `PATCH /bg-processes/:slug` (keyed by slug since [[TASK-0196]]; originally `:name`) returns 400 for `projectId: null`, a non-integer or an unknown project, while moving a process to another existing project is allowed; and `DELETE /projects/:id` **cascades**, returning 200 `{ ok: true, removedBgProcesses: string[] }` after deleting the project's `bg_processes` rows and the project in one transaction, then best-effort closing each removed process's tmux window and unlinking its `bg-<slug>.state` file. Existing `NULL` rows are backfilled by exact `workdir` match to a project's workdir by the idempotent, non-versioned `backfillBgProcessProjects(db)` in `host-server/db.ts`, run at `openDb`; unmatched or ambiguous rows are left `NULL` and warned about, and startup never fails. The frontend has no "Unassigned" group or option, and the project-delete confirmation lists the bg processes that will be removed. There is no Unassigned state in the API or UI. The schema-level `NOT NULL` + `ON DELETE CASCADE` rebuild landed with [[TASK-0196]] as schema v11 (see "Name uniqueness" below), with a deferred-nullable fallback when unmatched `NULL` rows exist. The restart guard ([[TASK-0194]]) keeps a fail-closed `unscoped` branch as a backstop. The live DB had 0 `NULL` rows on 2026-09-19. Rejected: visible-to-all (weakest guard), hidden (unreachable orphans) and, after the amendment, keeping policy C's repair state. derived_from::[[TASK-0186]]

### Name uniqueness

Outcome (decided 2026-09-20): bg process names are unique **per project**, not globally, and the addressable identity is a derived slug `<projectName>-<name>` (Option B). The bare `name` stays the display label. The slug is what the tmux window, `$LOG_DIR/bg-<slug>.log`, `$STATE_DIR/bg-<slug>.state`, the `/bg-processes/:slug` routes (including the restart route of [[TASK-0190]]), SSE payloads and `dev-commands status|tail` are keyed by, mirroring how agent windows are named (`agentWindowName()`). Because `-` is legal in project and process names, different pairs can yield the same slug, so create rejects a slug that collides with another bg slug or an existing agent window name. Since every bg process has a project (see "Unscoped bg processes" above), a single `(project_id, name)` unique index is enough once the column is `NOT NULL`; the `NULL`-distinct problem that would have needed a second partial index only exists transiently: schema v11 keeps `project_id` nullable (plus a partial unique index on `name WHERE project_id IS NULL`) when legacy rows cannot be matched to a project by workdir, so startup never fails, and `enforceBgProjectRequired()` promotes the column to `NOT NULL` on a later open once those rows are resolved. Implemented by [[TASK-0196]] (schema v11 rebuild, `bgSlug()`/`getBgBySlug()`/`listBgSlugs()`, routes, scripts, skill, frontend).

**Schema v11**: the rebuild drops the column-level `UNIQUE` on `bg_processes.name` (the `GLOB` `CHECK` is kept) and replaces it with the unique index `idx_bg_processes_project_name ON bg_processes(project_id, name)`, so two projects can each own a process called `dev`. `project_id` becomes `NOT NULL REFERENCES projects(id) ON DELETE CASCADE` when every existing row can be matched to a project by workdir. If any row cannot be matched, the migration does not fail or drop rows: `project_id` stays nullable, a partial unique index on `name WHERE project_id IS NULL` guards those rows, and the idempotent, non-versioned `enforceBgProjectRequired(db)` (run at `openDb`) promotes the column to `NOT NULL` on a later open once they are resolved. `PATCH` with a `projectId` change alters the slug, so it is rejected with 409 while the window is present.

**Slug-keyed surface**: `/bg-processes/:slug` routes (tail, PATCH, DELETE, `/window`, restart), SSE `bg-update`/`bg-removed` payloads (which carry `slug`), and `BgStatus.slug` all use the slug; `scripts/lib/db.sh` `load_bg` emits slugs, so `BG_NAMES`/`BG_DIRS`/`BG_CMDS` and the per-agent `AGENT_BG` values are slugs; `dev-commands status|tail` takes a slug (or a bare name when exactly one slug matches).

**Legacy files decision (2026-09-20)**: existing `$LOG_DIR/bg-<name>.log` and `$STATE_DIR/bg-<name>.state` files from before this change are left in place and ignored; there is no startup rename. Renaming would be a runtime file-moving side effect at host-server boot, and already-running bare-name windows must be recreated anyway (they no longer match a slug). Stale files can be deleted by hand.

Rejected: global uniqueness with a collision guard (forces hand-prefixed names like `myproj-dev`) and identity by numeric `id` (breaks the human-readable `dev-commands status dev` UX). derived_from::[[TASK-0188]]

### Restart mechanism and log capture

Outcome (measured 2026-09-20, tmux 3.7c, macOS 26.3, private sockets, two default shells): restart a bg process with `respawn-window -k -t <session>:=<slug> -c <workdir>` (no command) and then type the launch command; the `pipe-pane` attachment **survives** the respawn (same pane id, `#{pane_pipe}` stays 1, one `cat`), so log capture needs no re-attach in the normal case. `kill-window` + `new-window` drops the pipe (new pane, `pane_pipe=0`, nothing logged) and needs a re-attach that must happen **before** the command is typed, because attaching after typing loses first output when the client processes lose the race to the shell. `pipe-pane -o` on an already piped pane **toggles it off**, so any reattach guard reads `#{pane_pipe}` first and, when 0, runs `pipe-pane` **without `-o`** (replace semantics, no duplicate pipes in 3 repeated applies). `respawn-window -k` only hangs up the pty: a HUP/TERM-ignoring process survives as an orphan (`ppid 1`) under either mechanism, so a restart must capture the pane's descendant pids (macOS `pgrep` has no `-s`) and SIGKILL survivors after the respawn. The server writes the `--- restart <ts> ---` marker after the respawn returns and before typing the command, which is ordered 20/20 in both shells with no old-process output after it; a marker before the respawn is not, and a directly launched command or a `; exec $SHELL` wrapper changes what `#{pane_current_command}` liveness sees (crash closes the window, or the wrapper shell reads as `exited` while running). `display-message -t 'session:=gone'` exits 0 and answers for the current window, so window presence must come from `has-session -t` or `list-windows`. No control-mode (`-C`) client is used anywhere in the repo, so the reported tmux control-mode crash does not apply. The restart operation is [[TASK-0190]]; the exact ordered sequence is in its Approach. derived_from::[[TASK-0189]]

### Restart cooldown and audit (TASK-0193)

Outcome (implemented 2026-09-20): every `POST /bg-processes/:slug/restart` attempt is audited to `$LOG_DIR/bg-restarts.jsonl` and rate-limited for identified agent callers. Pure logic lives in `host-server/bgRestartPolicy.ts` (`evaluateCooldown`, `buildAuditRecord`, `parseCallerHeader`, `RestartHistory`).

- **Record fields:** `ts` (ISO), `bg` (slug), `callerKind` (`agent` | `dashboard`), `caller` (raw header value or `null`), `outcome` (`restarted` | `cooldown` | `failed` | `denied`), and when applicable `cooldownRemainingS`, `mechanism` (`respawn-window` | `new-window`, on success), `step` and `status` (on failure). `denied` (with a `reason` field) is the same-project guard of [[TASK-0194]], see the next section. A session-not-running 409 is logged as `failed` / `session-check`; an unknown-slug 404 is not logged. There is no rotation (one line per attempt, consistent with the other JSONL logs), a known limit.
- **Header convention:** `X-Conductor-Agent` carries the raw tmux window/agent name (`<project>-<name>` for project agents; `dev-commands` sends its `CONDUCTOR_AGENT_NAME`), trimmed, control characters stripped, capped at 128 chars, recorded verbatim. Absent or empty means a human/dashboard caller.
- **Cooldown:** `BG_RESTART_COOLDOWN_S` (default 30, `conductor.conf`). An identified agent caller gets 429 `{ error: 'restart cooldown', retryAfterS, lastRestartAt, lastRestartBy }` plus a `Retry-After` header when anyone restarted the process successfully less than the cooldown ago. Dashboard/header-less callers are exempt but still logged; a failed restart does not arm the cooldown. Last-success state is seeded lazily from the tail of `bg-restarts.jsonl`, so a host-server restart does not reset it. `BgStatus.lastRestart: { at, caller } | null` exposes the last success.
- **Caveat:** a guardrail against runaway restart loops, **not** authentication. The host-server is single-user localhost with no auth, so an agent that omits the header bypasses the agent cooldown and is logged as `dashboard`.

### Same-project restart guard (TASK-0194)

Outcome (implemented 2026-09-20): the restart route resolves the `X-Conductor-Agent` header **server-side** to an agent row and its `project_id`, and refuses a restart when that project does not match the bg process's project. Agents carry no project identifier of their own (only `CONDUCTOR_AGENT_NAME`, the tmux window name), so the check cannot be done client-side, and resolving on the server works for agents that are already running. The pure logic is in `host-server/bgAccess.ts` (`resolveCallerProject`, `authorizeRestart`); the route wiring and audit are in `host-server/index.ts`.

Resolution is exact string equality of the header against `agentWindowName()` for every agent (never prefix, substring or case-insensitive; `foo` does not match `foo-copy`). `<project>-<name>` concatenation is not injective (project `a-b` + agent `c` versus project `a` + agent `b-c`), so a header matching more than one agent is `ambiguous`.

| Caller | bg process | Result |
|--------|-----------|--------|
| No header (human/dashboard) | any | allow (still audited) |
| Agent in project P | project P | allow |
| Agent in another project, or with no project | project Q | 403 `project-mismatch` |
| Any agent, including a project-less one | no project | 403 `unscoped` (TASK-0186 policy `must-assign`; one-line switch `UNSCOPED_BG_POLICY`) |
| Header matches no agent | any | 403 `unknown-caller` (fail closed) |
| Header matches more than one agent | any | 403 `ambiguous-caller` (fail closed) |

A denial returns `403 { error, reason, callerProjectId, bgProjectId }`, does not touch tmux, does not arm the cooldown, and appends a `denied` record (with `reason`) to `bg-restarts.jsonl`. Check order is 404 unknown bg, 403 guard, 409 session not running, 429 cooldown, restart, so a denied caller never learns session or cooldown state. Reads (`GET /status`, tail, the project listing) and the open/close-window and PATCH/DELETE routes are not gated; they remain unauthenticated by design and are out of scope.

**Caveat:** not a security boundary. The identity is a self-declared header on a single-user, no-auth localhost server, so an agent that spoofs another agent's window name, or omits the header (treated as the dashboard), is not stopped. The guard keeps well-behaved agents inside their own project and fails closed on unresolvable identities. If agents ever run outside the host, the alternative is a signed per-agent token. derived_from::[[TASK-0194]]

### Agent-facing restart path (`dev-commands.sh restart`, TASK-0203)

Outcome (implemented 2026-09-20): agents restart a bg process through `skills/dev-commands/scripts/dev-commands.sh restart <name>`, a thin client over `POST /api/bg-processes/:slug/restart`. The script never runs tmux and makes no authorization or cooldown decision: the server owns the same-project guard ([[TASK-0194]]), the 429 cooldown ([[TASK-0193]]) and the `bg-restarts.jsonl` audit, so the script cannot be used to bypass them. It sends `X-Conductor-Agent: $CONDUCTOR_AGENT_NAME` whenever that variable is non-empty; with it unset the header is omitted and the server treats the call as the dashboard (guard and cooldown exempt, logged as `dashboard`), the same self-declared-identity caveat as above. There is no confirmation prompt (agents are non-interactive; the human confirmation lives in the dashboard) and no retry. The request uses a 60 s `curl` timeout (`RESTART_TIMEOUT_S`), longer than the read calls, because a restart is a tmux respawn plus the startup grace.

**Name resolution** (`<name>` is a slug as printed by `list`, or a bare process name): an exact slug wins; otherwise a bare name is matched within the caller's own project (project resolved via `GET /api/agents/whoami`, so `restart dev` never touches another project's `dev`); otherwise a bare name matching exactly one process machine-wide is used. An ambiguous bare name exits 1 and lists the candidates. Since [[TASK-0204]], `status` and `tail` use the same resolver online (so `status dev`, `tail dev` and `restart dev` agree) but keep their historical exit 2 for ambiguity; offline they resolve bare names against the state-file names only. Without `jq`, only an exact slug is accepted and the script says so.

**Exit-code contract** (success line on stdout, everything else on stderr):

| Code | Server answer | Meaning for the agent |
|------|---------------|-----------------------|
| 0 | 200 | Restarted; `tail <slug>` to watch it come back up |
| 1 | 404, or client-side | Usage error, unknown process, or ambiguous bare name |
| 2 | no response | Host-server unreachable (no offline fallback) |
| 3 | 403 | Refused: other project, or caller identity unresolved; do not retry |
| 4 | 409 | The conductor tmux session is not running; nothing to restart |
| 5 | 429 | Cooldown; never retried (a looping agent is exactly what the cooldown stops), the message says to `tail` and wait `retryAfterS` |
| 6 | 500 or any other status | Restart failed on the server (prints `error` and `step`) or an unexpected response |

Coverage: `scripts/verify-dev-commands-restart.sh` runs the script against a stub HTTP server (every status above, header forwarded verbatim, exactly one request on 429, project-scoped bare-name resolution, ambiguous name, unreachable port, no-`jq` path; 71 checks at [[TASK-0203]], extended by [[TASK-0204]] with the online `status`/`tail`/`list` cases). [[TASK-0208]] wires it into the aggregate verify run; a live smoke recipe is deferred to that task's UAT. Etiquette for the agent reader (diagnose with `status`/`tail` first, restart once then observe, never loop) lives in `skills/dev-commands/SKILL.md`. implements::[[TASK-0203]] builds_on::[[TASK-0190]]

### Agent-facing status and tail (TASK-0204)

Outcome (implemented 2026-09-20): `dev-commands.sh status` and `tail` moved from the state file and a raw `tail -n` of the log onto the server's own signals. `status` is online-first and reports `BgStatus.liveness` (`running` / `exited` / `stopped`) as the authoritative field, with the window, `lastRestart` and the poll-lagged state file beside it, because the state file can still say `running` for a process that has crashed back to a shell. `tail` reads the ANSI-stripped text endpoint (restart markers included) and passes `-n` through (positive integer, clamped to the server's 1000). Offline, `status` prints the state file interpreted in the `running` / `exited` / `dead` vocabulary (flagging pre-[[TASK-0191]] `alive`/`idle`/`busy` values as legacy) and `tail` reads `bg-<slug>.log` through a best-effort `sed` escape strip, so an offline agent still gets readable output but not the server's cleaning or restart markers. `SKILL.md`'s earlier `idle/busy/running` vocabulary was never what the monitor wrote and has been replaced. `list` lines carry the liveness value. implements::[[TASK-0204]] builds_on::[[TASK-0203]]

### linked_agent_id

Outcome (decided 2026-09-19): retire the single-agent link `bg_processes.linked_agent_id` (nullable FK to `agents(id)`, `ON DELETE SET NULL`); `project_id` is the sole access boundary. Nothing replaces the `CONDUCTOR_BG_NAME`/`LOG`/`STATE` env injection: the project-scoped `dev-commands` skill (list/status/tail, plus the restart and ANSI-stripped output endpoints in ROADMAP-0024) is the only agent interface. Env vars are frozen at agent launch, so a project-level env var set would go stale as soon as a bg process is added or renamed. The env vars were set only by `scripts/conductor.sh` and `scripts/spawn.sh` (via the `LEFT JOIN` in `scripts/lib/db.sh::load_agents`); the host-server never set them for dashboard-spawned agents, and no skill, rule, `CLAUDE.md` or agent prompt in the repo reads them (`~/.claude/rules/` was not scanned; the two rule files loaded into context do not mention them). The live DB has 0 linked rows.

Status (2026-09-20): [[TASK-0197]] has landed, so no code reads or writes the column any more (`createBgProcess` takes no link, `BgProcess`/`BgStatus`/the SSE diff carry no link field, `load_agents` no longer joins `bg_processes`, `conductor.sh`/`spawn.sh` inject no `CONDUCTOR_BG_*`, `AGENT_BG_LINKS` is gone from `conductor.conf`/`config.ts`/`seedFromLegacy`); a stale `linkedAgent`/`linkedAgentId` in a POST/PATCH body is ignored. The column itself was then dropped by [[TASK-0198]] (see "Schema v12" below).

Staged so the column is never dropped while code still reads it: [[TASK-0197]] removes every reader and writer (form input, API/status/SSE fields, env injection, legacy `AGENT_BG_LINKS`/`linkedBg`) and leaves the column unused; [[TASK-0198]] then drops it with a table-rebuild migration (SQLite cannot `DROP COLUMN` a column with a `REFERENCES` clause), seeding `project_id` from the linked agent's project where it is still `NULL`. [[TASK-0196]] had already shipped as schema v11, so the drop is its own version (see "Schema v12" below). Rejected: keep as-is (two overlapping access concepts and a form input promising env vars nothing reads) and deprecate-but-keep (preserves the dead concept the decision exists to remove). derived_from::[[TASK-0187]]

**Schema v12** (2026-09-20, [[TASK-0198]]): `linked_agent_id` is gone from `bg_processes`. `rebuildBgProcesses()` in `host-server/db.ts` now never copies the column, so every rebuild (the v11 one, the v12 one, and the non-versioned `enforceBgProjectRequired`) omits it and it cannot be rebuilt back in; the fresh-install DDL no longer creates it. Before any rebuild, `seedBgProjectFromLinkedAgent()` sets `project_id` from the linked agent's project on rows where it is still `NULL` (rows that already have a project are never overwritten). The v12 step only rebuilds when the column is still present (a fresh DB, or one already rebuilt by v11, just gets the version bump), and it handles both table shapes (nullable `project_id` plus the partial `idx_bg_processes_null_name`, and `NOT NULL`), preserving `idx_bg_processes_project_name`, the `GLOB` `CHECK` and `ON DELETE CASCADE`. Rows still `NULL` after the seed do not abort the migration (unlike the task's original wording): startup never fails on unmatched rows, matching the v11 design, and they are left for the workdir backfill. derived_from::[[TASK-0198]]
