# Discovering All Active Claude Code Sessions on a Machine

Three ways to answer "what Claude Code sessions are currently running here," ranked by how much they lean on a documented contract versus a reverse-engineered one:

1. **`claude agents --json`** (recommended) — officially documented (`code.claude.com/docs/en/agent-view`, confirmed via Context7 2026-09-13): "prints active sessions as a JSON array and exits: every live session, plus background sessions that are still working or blocked even when their process has exited." Scoped to the whole machine by default; `--cwd <path>` narrows to one directory tree; `--all` includes completed background sessions. **Documented field presence rules** (not just an empirical sample): `cwd`/`kind`/`startedAt` always present; `id` only on background sessions (usable with `claude attach`/`claude logs`/`claude stop`); `state` only on background sessions, one of `working`/`blocked`/`done`/`failed`/`stopped`; `pid`/`status` present only while the process is alive; `waitingFor` present when `status` is `waiting` (values: `permission prompt`, `input needed`, `sandbox request`, `worker request`, `dialog open`); `sessionId`/`name` present when set. No tmux dependency, no env-var setup, works for any session regardless of how it was launched. See `derived_from::[[Claude Code CLI]]`.
2. **`~/.claude/sessions/<pid>.json`** — the undocumented internal registry `claude agents --json` is itself built on: one file per live session, garbage-collected by Claude Code's own local daemon on process exit. Carries extra fields (`updatedAt`, IPC `messagingSocketPath`) but is a private format with no stability contract — a fallback only, not a first choice. Likewise `~/.claude/daemon/roster.json` is an internal, narrower structure (see Verification note below) — the officially documented way to inspect the supervisor is `claude daemon status` ("Print the supervisor's state, version, socket directory, and worker count"), not parsing that file directly.
3. **Building your own registry via `SessionStart`/`SessionEnd` hooks** — redundant given (1) already exists, and reintroduces exactly the "stale entry survives a SIGKILL/crash/sleep" class of bug a daemon-maintained roster already avoids. `SessionEnd` reliability gaps are now confirmed with real citations, not just inferred — see the Verification note. Only worth it if the `claude` binary genuinely isn't available to the caller (see `relates_to::[[Claude Code Hooks]]` for why tmux-conductor's own globally-installed hooks *don't* already give this for free — they no-op without conductor-specific env vars or a tmux pane).

**Detection and control turn out to be less separate than first thought.** Beyond `claude agents --json`, official "agent view" also documents a full shell-scriptable control surface keyed by a background session's `id`: `claude attach <id>` (attach to it in this terminal), `claude logs <id>` (recent output), `claude stop <id>` / `claude kill` (stop it), `claude respawn <id>` / `claude respawn --all` (restart, resuming the saved conversation), `claude rm <id>` (remove from the list; transcript stays on disk). **This closes most of the "no control channel" gap for background sessions specifically** — a detected background session's `id` is directly actionable without any tmux-pane correlation. It does *not* extend to plain `interactive` sessions (no `id` field, no `attach`/`stop`/`respawn` equivalent documented) — those still need a tmux-pane walk to drive from outside their own terminal. A dashboard built on this data should treat detected *interactive* sessions as read-only, but can offer real actions (attach/stop/logs) for detected *background* sessions.

**Privacy/scope caveat**: because `claude agents --json` is machine-wide by default, surfacing it unconditionally in a project-scoped dashboard would leak cwd/status for every unrelated project the user has open elsewhere. Scope with `--cwd` or an explicit allowlist before defaulting a feature like this to "on."

See `relates_to::[[Claude Code CLI]]`, `relates_to::[[Claude Code Hooks]]`, `relates_to::[[agent-state-determination]]`, `relates_to::[[controlling-detected-claude-code-sessions]]`.

## Identification/categorization is reliable — verified live (2026-09-13)

`derived_from::[[host-agent-identification-and-control]]` closed the "detection ≠ control" open question above with a concrete, empirically-verified method rather than leaving pane-location as unknown. A session's controlling tty (`ps -o tty= -p <pid>`) cross-referenced against `tmux list-panes -a -F "#{pane_tty} #{session_name}:#{window_index}.#{pane_index}"` (across **every** tmux session on the server) gives an exact three-way split: **tmux-hosted** (exact pane found), **plain-terminal** (a real tty, absent from any pane), or **headless/background** (no tty at all — confirmed on a live `kind:"background"` session). Verified with two exact live matches on the research machine.

**Caught mid-investigation**: three pids initially looked like orphaned survivors of a closed tmux window (empty tty field) — re-checked with `kill -0` first and found they'd simply exited. `ps -o tty=` returns an empty string for both "no controlling terminal" and "no such process"; always gate on liveness before interpreting it.

This means a "Detected Sessions" kanban feature (proposed in the prior research round) can show an exact tmux location when one exists, not just cwd/name/status — and, per `relates_to::[[controlling-detected-claude-code-sessions]]`, that location is what determines whether the session can actually be driven.

## Verification note (2026-09-13) — a peer research agent's follow-up, checked via Context7 + Brave Search before trusting

A second `claude-code-guide` agent run added claims to this topic. Rather than accept or dismiss them wholesale, each was checked — first by direct CLI/file inspection, then against official docs via Context7 (`/websites/code_claude`) and against GitHub via Brave Search. Result: a genuine mix of one fabrication and several real, citable facts — worth recording precisely rather than as a blanket "unverified":

- **False, confirmed by direct CLI check**: `claude sessions list --json` does not exist. `claude --help`'s full top-level command list has no `sessions` entry at all (`agents, auth, auto-mode, doctor, gateway, import, install, mcp, plugin, project, setup-token, ultrareview, update`), and `claude sessions --help` / `claude sessions list --help` both silently fall through to the generic top-level usage banner — the exact same failure mode as the already-documented `claude usage` bug (`relates_to::[[Claude Code CLI]]`). The claimed doc page `code.claude.com/docs/en/sessions.md` does not describe this command; the real doc for `claude agents --json` lives at `code.claude.com/docs/en/agent-view`.
- **Corroborated, with the exact timing right**: `claude agents --json` shipping "May 2026" is confirmed by an official what's-new post, `code.claude.com/docs/en/whats-new/2026-w21` (Context7, 2026-09-13): "`claude agents --json` lists live sessions as JSON for scripting, such as status bars and session pickers." The specific version-number gate ("v2.1.145+") was still not independently confirmed (changelog didn't surface a version number), so don't repeat that exact figure as fact.
- **Inaccurate as characterized by the peer agent, corrected by direct file inspection**: `~/.claude/daemon/roster.json` is **not** "the authoritative running-session roster" for every session — its `workers` dict held only 2 entries (both `bg-pty-host`/spare-pty-pool workers) while 14 `claude` processes were concurrently running per `ps`. The *officially documented* way to inspect supervisor state is `claude daemon status`, not parsing this internal file.
- **Corroborated independently**: "Agent View" is the real, official name for this feature (`claude agents --help`'s own text: "Default agent for sessions dispatched from **agent view**"; confirmed as the doc page title too).
- **Confirmed true, with real citations found via Brave Search** (both peer-cited issue numbers are genuine, on-topic, and open/closed-as-duplicate-but-still-live bugs, not hallucinated):
  - `anthropics/claude-code#41577` — "SessionEnd hooks are killed before completion when running async work," even with a 90s timeout configured. Matches the official docs' own 1.5s-default/60s-max timeout mechanics (`CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS`, confirmed via Context7).
  - `anthropics/claude-code#62987` — "`claude rm`/`stop`/reap SIGKILLs background session tree without SIGTERM grace" — teardown delivers SIGKILL immediately, no prior SIGTERM, orphaning locks cleanup code can't run to release. Directly substantiates "a stop/crash won't reliably run your SessionEnd cleanup."
  - Also found independently while checking: `#6428` ("SessionEnd hook does not fire with `/clear` as documentation states") and `#17885`/`#35892` ("SessionEnd hook doesn't fire on `/exit`") — further, separately-filed reliability gaps in the same hook, reinforcing the same conclusion from a different angle.
  - The official `reason` enum for `SessionEnd` (Context7, `code.claude.com/docs/en/hooks`) is `clear`, `resume`, `logout`, `prompt_input_exit`, `other` (`bypass_permissions_disabled` removed in v2.1.234) — hooks "have no decision control" and Claude Code "discards their JSON output fields."
  - The ~30-second daemon PID-reaper claim remains unconfirmed by any source found — still don't cite it as fact.
- `~/.claude/jobs/<id>/state.json` was independently re-confirmed (already known from `derived_from::[[bug-0001-background-agent-detection]]`) — rich per-background-job state including `state`/`tempo`/`inFlight`/`linkScanPath`/`intent`/`sessionId`. Nothing new here beyond what was already in the wiki.

**Lesson**: a peer agent's research report mixed one confidently-stated fabricated subcommand with several genuine, correctly-cited GitHub issues in the same message. Neither blanket trust nor blanket dismissal was correct — each specific claim needed its own check (CLI invocation, Context7 doc lookup, or Brave Search for the citation) before being repeated as fact.
